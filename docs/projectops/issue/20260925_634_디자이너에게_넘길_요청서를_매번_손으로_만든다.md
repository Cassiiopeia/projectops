📝 현재 문제점
---

- 요즘 개발 흐름은 **AI가 먼저 화면을 만들고 시안은 나중에 온다.** 또는 디자이너가 "어떻게 그려야 할지 모르겠다"고 한다. 그때 디자이너에게 보내는 요청서를 매번 손으로 만든다.
- 실례: Twin-Fang/elum #418(앱 버전 표시를 임시로 구현) → #419(디자인 시안 요청). 사람이 한 일은 다음과 같다.
  1. 실제 화면 렌더 캡처 (로그인 iOS·Android, 설정)
  2. 대안 목업 4안 + 3안을 실제 컴포넌트로 렌더
  3. 작은 글자 4배 확대 조각 + 비교 보드 합성
  4. "꼭 지킬 것", "개발 쪽 추천", "고르면 개발이 더 드는 안"을 본문에 정리
  5. 이미지 업로드 → 디자인 이슈 등록 → 디자이너 배정
- **디자이너는 보통 기본 화면만 그린다.** 목록이 있을 때만 그리고, 비었을 때·실패했을 때·글자가 길 때는 빠진다. 손으로 만든 요청서도 이 부분을 자주 놓친다.
- 반면교사: #535에서 `design`, `design-analyze` 스킬이 **산출물 실적이 없어서** 삭제됐다. 새 스킬은 반드시 디자이너가 받아 보는 결과물로 끝나야 한다.

🛠️ 해결 방안 / 제안 기능
---

`pro-design-brief` 작업 스킬을 신설한다. 디자이너에게 **정답이 아니라 생각할 재료**를 넘긴다.

```
0 설정 판정 → 1 입력 파악 → 2 상태 목록 → 3 캡처(pro-launch) → 4 대안·문구·UI 요소 → 5 보드(HTML→PNG) → 6 게시(승인 게이트)
```

- 선행: #629 (pro-launch), #632 (render), #630 (Figma 읽기 공용 규칙)
- 설계 전문: `docs/superpowers/specs/2026-09-25-pro-design-brief-design.md`

⚙️ 작업 내용
---

**0. 설정 (`design_brief` 독립 섹션)**
- [ ] `destination`(`issue` | `html` | `markdown`) · `designer` · `auto_approve`, 전역 기본값 + `projects[]`(`match` = GitHub `owner/repo` 또는 레포 절대경로)
- [ ] GitHub을 쓰지 않는 레포도 동작해야 한다. 그래서 `github` 아래에 두지 않는다
- [ ] 처음 한 번 자동 판정 → 애매하면 한 번에 한 질문 → 저장, 이후 자연어("다음부턴 HTML로")로 변경. 설정 키 이름과 경로는 사용자에게 보여주지 않는다 (`approval-and-questions.md`, `config-rules.md`)
- [ ] 디자이너 자동 판정: `.github/ISSUE_TEMPLATE/*`의 `디자인:` 줄, 최근 디자인 이슈 담당자
- [ ] `config-rules.md` §7 스키마 표, `config.json.example` 예시 추가

**1. 입력 파악**
- [ ] 대화 맥락 우선 (특히 "왜 이 자리를 골랐나"는 대화에만 있다)
- [ ] 구현 여부 판정: 구현됨 / 일부 / 아직 없음
- [ ] Figma 링크가 있으면 #630 공용 규칙으로 읽는다
  - 시안에 그려진 상태 vs 빠진 상태 **빈틈 표**
  - 토큰·컴포넌트를 대안 목업에 사용
  - 보드에 `시안 | 현재 구현 | 대안` 세 칸
  - 시안끼리 어긋난 곳은 **고치지 않고 질문으로** 올린다
- [ ] 이미지(참고 화면)가 있으면 "참고" 칸

**2. 상태 목록**
- [ ] 5축(데이터 · 입력 · 환경 · 사람 · 표시), agent가 코드를 읽어 뽑는다 (스크립트 스캔 금지)
- [ ] 상태마다 구현됨 / 임시 / 미구현 표시. 이 화면에 해당하는 축만 넣는다

**3. 캡처**
- [ ] `launch_cli.py get-output-path --skill design-brief`, `render run` → `app shot` / `web shot` + `web route` → ASCII
- [ ] 대안 목업도 **실제 컴포넌트로** 렌더한다 (HTML로 다시 그리면 글꼴·간격이 달라진다)
- [ ] 작은 요소는 확대 조각을 만든다

**4. 대안 · 문구 · UI 요소 · 꼭 지킬 것**
- [ ] 배치 대안 3~5안: 의미 있는 축(위치 · 밀도 · 표현 · 진입)에서 가른다. "현재 구현"과 "최소" 안을 항상 포함한다. 안마다 장점 · 약점 · 개발 영향, 추천은 근거와 함께 한 줄
- [ ] 문구표 `현재 → 후보 2~3 → 이유`
  - AI 티: 번역투, 장황, em dash·가운뎃점 남발, 과장
  - 레포 용어·말투 규칙은 루트·모듈 `CLAUDE.md`, 디자인 원칙 문서에서 자동으로 읽는다
  - 법적 문구는 "바꾸면 안 됨" 표시만 하고 후보를 내지 않는다
  - 없는 상태별 문구는 "문구 필요"로 표시한다
- [ ] UI 요소 후보: 데이터 모양(하나 고르기 · 여러 개 · 긴 내용 · 확인·알림 · 목록)별 후보. 레포에 있는 컴포넌트를 먼저 쓰고, 없는 것은 "새 컴포넌트"로 표시
- [ ] 꼭 지킬 것 자동 수집: 브랜드 규격, 최소 터치 크기, 레포 디자인 원칙, 합의된 예외. 출처를 함께 적는다

**5. 보드**
- [ ] `assets/board.html` 템플릿 + 데이터 JSON, 7구성: 요약("정답이 아니다") · 현재 구현 · 상태 격자 · 대안 비교 · 문구표 · UI 요소 · 개발 영향
- [ ] PNG는 pro-launch의 Chromium으로 **주제별로 나눠** 뽑는다 (한 장 폭 ≤ 3,400px). 안 이름은 A·B·C로 통일한다

**6. 게시**
- [ ] `issue`: pro-github 스크립트로 `upload-image` → `create-issue` (디자인 템플릿 🖌️🎯📋💡🙋), 담당자 = designer, 구현 이슈와 서로 링크
- [ ] `html`: 보드 HTML 한 페이지 (이미지 내장, 상태와 문구 후보는 탭으로)
- [ ] `markdown`: md + PNG 폴더
- [ ] **디자이너에게는 한 형식만 준다**
- [ ] 게시 직전 승인 게이트 A/B/C (`approval-and-questions.md` §4)

**스크립트 `design_brief_cli.py`** (판단은 agent, 스크립트는 실행·기록)
- [ ] `config show|set` · `get-output-path` · `board --data --out [--png]` · `copy-lint --file`(기계적 검사만) · `ascii --spec`
- [ ] `EVIDENCE_SKILLS`에 `design-brief`, `CLI_TO_SKILL`에 `design_brief_cli.py → pro-design-brief`

**실패 경로**
- [ ] 브라우저가 없으면 md 표 + 원본 캡처
- [ ] 렌더에 실패한 상태는 ASCII + "렌더 실패" 표시
- [ ] 업로드에 실패하면 로컬 산출물 경로를 안내
- [ ] Figma 읽기에 실패하면 Figma 없이 진행하고 요약에 적는다
- [ ] 디자이너를 모르면 담당자 없이 등록하고 알린다
- [ ] residue는 보고만 하고 지우지 않는다

**하지 않는 것**
- 캡처용 AI 생성 API 호출, Figma에 그리기(MCP 읽기 전용), 디자이너 대신 결정, 법적 문구 후보 제안
