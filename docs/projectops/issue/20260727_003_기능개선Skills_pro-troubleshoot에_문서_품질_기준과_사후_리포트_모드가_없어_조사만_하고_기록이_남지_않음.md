📝 현재 문제점
---

`pro-troubleshoot`은 가설 수립과 검증이라는 좋은 분석 프레임을 갖고 있습니다. 하지만 **조사한 결과가 나중에 쓸 수 있는 형태로 남지 않습니다.**

구체적으로 네 가지가 빠져 있습니다.

**첫째, 문서 품질 기준이 없습니다.** 산출물을 저장하라고만 되어 있고, 그 문서가 어떤 조건을 만족해야 하는지가 없습니다. 그래서 명령어가 상대경로로 적히거나, "이렇게 하면 된다"만 있고 왜 그런지가 빠진 문서가 나와도 걸러지지 않습니다. 몇 달 뒤 같은 문제를 만난 사람이 그 문서만으로 해결하지 못합니다.

**둘째, 이미 해결한 문제를 문서화하는 경로가 없습니다.** 현재 프로세스는 문제 정의부터 시작합니다. 그런데 실제로는 대화 중에 문제를 이미 다 풀어놓고 "방금 한 거 정리해줘"라고 요청하는 경우가 많습니다. 이때 스킬을 부르면 이미 끝난 조사를 처음부터 다시 합니다.

**셋째, 되돌릴 수 없는 작업 전 백업 안내가 없습니다.** 설정 파일 수정, 서비스 재시작, 스키마 변경 같은 조치를 제시하면서 백업 절차를 함께 주지 않습니다. 조치가 잘못됐을 때 돌아갈 방법이 문서에 없습니다.

**넷째, 무엇부터 확인할지에 대한 가이드가 없습니다.** 가설을 세우라고 하지만, 서버 문제인지 빌드 문제인지에 따라 먼저 볼 것이 다릅니다. 매번 처음부터 생각해야 합니다.

🛠️ 해결 방안 / 제안 기능
---

별도 스킬을 새로 만들지 않고 **`pro-troubleshoot`을 보강**합니다. 트러블슈팅과 그 기록은 같은 작업의 앞뒤이므로, 나누면 사용자가 매번 어느 쪽을 불러야 할지 판단해야 합니다.

**1. 작업 모드 구분**

호출 시점에 문제가 진행 중인지, 이미 해결됐는지를 먼저 판별합니다.

| 모드 | 판별 기준 | 동작 |
|---|---|---|
| 실시간 | "안 돼", "에러 났어" 등 현재 진행형 | 전체 프로세스 수행 |
| 사후 기록 | "아까 그거 정리해줘" 등 | 대화 맥락에서 조사 결과를 먼저 추출하고, 빠진 정보만 보충 |

사후 기록 모드에서 이미 끝난 조사를 반복하지 않는 것이 핵심입니다.

**2. 문서 품질 기준 명시**

산출물이 만족해야 할 조건을 규칙으로 둡니다.

- 시간이 지난 뒤 다른 사람이 이 문서만으로 같은 문제를 해결할 수 있어야 한다
- 명령어는 복사해서 바로 실행 가능해야 한다 (경로를 구체적으로)
- "왜 이 문제가 생겼는지", "왜 이 해결이 맞는지"를 적는다
- 증거 없이 원인을 단정하지 않는다. 불확실하면 추정이라고 표시한다

**3. 백업 우선 원칙**

되돌릴 수 없는 조치를 제안할 때는 백업 절차를 함께 제시합니다. 설정 변경, 서비스 재시작, 스키마 변경 등이 해당합니다.

**4. 카테고리별 확인 항목**

문제 유형별로 먼저 볼 항목을 reference 문서로 정리합니다. 이 프로젝트가 지원하는 타입(Spring, Flutter, React, Node, Python)에 맞춰 작성하며, 특정 회사나 제품에 종속된 경로·도구는 넣지 않습니다.

**5. 기존 사례 확인 단계**

새로 조사하기 전에 이전에 같은 문제를 다룬 문서가 있는지 먼저 확인합니다.

⚙️ 작업 내용
---

- `skills/pro-troubleshoot/SKILL.md`: 모드 구분, 문서 품질 기준, 백업 원칙, 기존 사례 확인 단계를 기존 가설-검증 프레임에 통합
- `skills/references/` 하위에 카테고리별 확인 항목 문서 신설
- 기존 프로세스(문제 정의 → 정보 수집 → 원인 분석 → 해결책 → 검증)와 Quick Fix / Root Fix 구분은 유지

**참고 — 착안 출처**

사내에서 별도로 운용하던 트러블슈팅 리포트 스킬이 위 네 가지를 이미 갖추고 있어, 그 설계를 참고했습니다. 다만 특정 제품 전용 경로, 사내 시스템 연동, 특정 언어 편중 부분은 가져오지 않고 이 프로젝트의 다중 타입 지원에 맞게 다시 씁니다.
