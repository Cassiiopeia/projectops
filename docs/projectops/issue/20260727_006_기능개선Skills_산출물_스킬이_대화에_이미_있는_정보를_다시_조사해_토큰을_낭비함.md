📝 현재 문제점
---

산출물을 만드는 스킬이 **이미 대화에 있는 정보를 처음부터 다시 조사합니다.**

전형적인 흐름은 이렇습니다. 사용자와 함께 문제를 파악하고, 코드를 고치고, 검증까지 마칩니다. 그 과정에서 무엇이 왜 바뀌었는지가 대화에 전부 남아 있습니다. 그런데 이 상태에서 보고서를 요청하면 스킬이 `git status`부터 다시 실행하고, 변경된 파일을 다시 읽고, 무엇이 바뀌었는지 다시 분석합니다.

같은 정보를 두 번 확보하는 셈이라 토큰이 그만큼 더 듭니다. 작업이 길었을수록 낭비가 큽니다.

`pro-testcase`에는 이미 "대화 컨텍스트나 `git status`로 구현 내용 파악 (이미 알고 있으면 별도 조사 불필요)"이라는 문구가 있습니다. 다른 산출물 스킬에는 이 원칙이 없습니다.

**두 번째 문제는 작업 성격에 맞지 않는 모델을 쓰게 된다는 점입니다.**

보고서 작성, 테스트케이스 생성 같은 작업은 **이미 확보된 내용을 정리하는 일**입니다. 새로운 판단이나 설계가 거의 없습니다. 그런데 사용자가 구현 작업을 위해 상위 모델을 선택해 둔 상태라면, 정리 작업에도 그대로 그 모델이 쓰입니다.

`pro-changelog-deploy`에는 이미 다음 안내가 있습니다.

> 이 스킬은 릴리스 노트 작성이 주 작업이다. lite 모델로 실행을 권장한다. 커밋 분석과 자연어 재작성만 하면 되므로 강력한 모델이 불필요하다.

같은 성격의 다른 스킬에는 이 안내가 없어, 사용자가 판단할 근거를 얻지 못합니다.

🔄 재현 방법
---

1. 여러 파일을 수정하는 작업을 대화로 진행해 완료한다
2. 무엇을 왜 바꿨는지가 대화에 모두 남은 상태에서 보고서를 요청한다
3. 스킬이 `git status`를 실행하고 변경 파일을 다시 읽는다
4. 대화에 이미 있던 내용을 다시 확보하느라 토큰이 추가로 소모된다

🛠️ 해결 방안 / 제안 기능
---

**1. 대화 맥락 우선 원칙을 산출물 스킬에 명시**

조사를 시작하기 전에 대화에 이미 답이 있는지 확인하고, 있으면 그것을 사용합니다. 부족한 부분만 보충 조사합니다.

```
대화에 이미 있는 것   → 그대로 사용 (재조사 금지)
대화에 없는 것        → 그것만 조사
대화 없이 호출된 경우  → 기존대로 처음부터 조사
```

`pro-testcase`가 이미 쓰고 있는 방식이며, 이를 다른 산출물 스킬로 넓힙니다.

**2. 작업 성격에 맞는 모델 권고 추가**

스킬마다 요구하는 판단 수준이 다르므로, 일률적으로 낮추지 않고 성격에 맞춰 나눕니다.

| 스킬 | 주 작업 | 권고 | 이유 |
|---|---|---|---|
| `pro-changelog-deploy` | 커밋을 짧은 릴리스 노트로 재작성 | lite (이미 적용됨) | 기술 용어를 덜어내는 축약 작업 |
| `pro-testcase` | 구현 내용을 표 형식 절차로 변환 | lite | 정해진 형식에 채워 넣는 변환 작업 |
| `pro-report` | 무엇을 왜 바꿨는지 설명 | **중간 등급** | 아래 참조 |

**`pro-report`를 lite로 내리지 않는 이유**가 있습니다. 보고서의 가치는 요약이 아니라 **설명**에 있습니다. "무엇을 바꿨다"는 diff를 보면 알 수 있지만, "왜 이 방식이어야 했는지", "이 부분을 나중에 건드리면 왜 위험한지" 같은 내용은 판단이 필요합니다. 실제로 이 저장소의 보고서들은 주의사항 절에 후속 작업자를 위한 함정을 적어두는데, 이것이 보고서를 쓰는 주된 이유입니다.

따라서 `pro-report`에는 "최상위 모델까지는 불필요하지만 축약 전용 모델도 부적합하다"는 취지의 안내를 답니다. 디테일이 손실되면 보고서를 쓰는 의미가 사라지기 때문입니다.

반면 `pro-review`(다관점 분석), `pro-note`(원인 추적), `pro-analyze`(영향 범위 판단)는 실제 판단이 핵심이므로 권고를 달지 않습니다.

⚙️ 작업 내용
---

- `skills/pro-report/SKILL.md` — 대화 맥락 우선 원칙 추가, 모델 권고 추가
- `skills/pro-testcase/SKILL.md` — 모델 권고 추가 (맥락 원칙은 이미 있음)
- `skills/references/approval-and-questions.md` — 산출물 스킬 공통 원칙으로 "대화에 이미 있는 정보는 다시 조사하지 않는다" 명시

**참고 — 모델 권고의 한계**

이 안내는 실행 모델을 자동으로 바꾸지 않습니다. 사용자가 보고 판단하는 근거이며, 하네스가 스킬별 모델 지정을 지원하게 되면 그때 실제 적용 지점이 됩니다. 반면 대화 맥락 재활용은 모델과 무관하게 즉시 효과가 있습니다.
