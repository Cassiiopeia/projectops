📝 현재 문제점
---

어렵게 알아낸 것이 **매번 휘발됩니다.**

빌드가 깨져서 반나절을 쓰거나, 라이브러리 사용법을 삽질 끝에 파악하거나, 이 프로젝트만의 관례를 겨우 알아냅니다. 그런데 그 결과가 어디에도 남지 않습니다. 몇 달 뒤 같은 벽을 만나면 처음부터 다시 파헤칩니다.

기존 `pro-troubleshoot`은 이 문제를 풀지 못합니다.

**첫째, 대상이 좁습니다.** 코드 버그를 잡는 스킬이라 가설을 세우고 검증해 Quick Fix와 Root Fix를 코드로 제시합니다. 그런데 실제로 반복되는 소모는 코드 버그만이 아닙니다.

- 배포가 실패했는데 원인이 인증서 만료였다
- 이 라이브러리는 이런 순서로 호출해야 한다
- 이 프로젝트는 이런 패턴을 쓴다
- 이 API에 문서에 없는 제약이 있다
- 로컬 환경에서만 이 설정이 필요하다

전부 다시 알아내는 데 시간이 드는 것들인데, 코드 디버깅 프레임에 담기지 않습니다.

**둘째, 기록이 남지 않습니다.** 산출물 저장 규칙은 있지만 그 문서가 어떤 조건을 만족해야 하는지가 없습니다. 실제로 이 저장소에 쌓인 문서는 1건뿐입니다.

**셋째, 과거를 찾아보지 않습니다.** 막혔을 때 "이거 전에 겪었나?"를 확인하는 단계가 없습니다. 쌓아둔 것이 있어도 꺼내 쓰지 못합니다.

🛠️ 해결 방안 / 제안 기능
---

알아낸 것을 쌓고, **막혔을 때 자동으로 꺼내 쓰는** 스킬 `pro-note`를 신설합니다.

### 두 시점에 자동으로 개입한다

별도로 호출하지 않아도 동작합니다.

**시점 1. 막혔을 때 — 과거를 먼저 뒤진다 (핵심)**

"뭔가 안 된다", 빌드·배포 실패, 에러 로그를 붙여넣는 상황이면 **조사를 시작하기 전에** 기록을 검색합니다.

```
"배포가 또 실패하는데?"
  ↓
기록 검색 (저장소 + 홈)
  ↓
[발견] 3개월 전 같은 증상 — 인증서 만료가 원인이었음
  ↓
"전에 겪은 문제로 보입니다. 그때는 인증서 만료가 원인이었고
 갱신 후 해결됐습니다. 먼저 만료일부터 확인할까요?"
```

이것이 축적의 실제 목적입니다. 기록은 이 순간을 위한 재료이며, 검색이 동작하지 않으면 쌓아둔 것이 의미가 없습니다.

**시점 2. 어렵게 알아냈을 때 — 기록을 제안한다**

해결된 모든 건을 기록하지 않습니다. **고생한 흔적이 있을 때만** 제안합니다.

| 기록 제안함 | 제안하지 않음 |
|---|---|
| 시도를 여러 번 반복했다 | 한 번에 끝났다 |
| 원인이 처음 예상과 달랐다 | 예상대로였다 |
| 조사가 여러 단계로 길어졌다 | 즉시 답이 보였다 |
| 검색해도 과거 기록이 없었다 | 기존 기록으로 해결했다 |

한 번에 끝난 일은 남길 가치가 없고, 매번 물으면 오히려 방해가 됩니다.

**명시적 호출**

`/pro-note`를 직접 부르면 전체 흐름(검색 → 정리 → 기록)을 수행합니다. 이미 해결한 것을 나중에 기록하는 용도로도 씁니다.

### 기록을 두 종류로 나눈다

| 종류 | 무엇을 담나 | 예시 |
|---|---|---|
| **case** | 무슨 일이 있었나 (증상·조사·원인·조치·검증) | 배포 실패 → 인증서 만료였음 |
| **fact** | 무엇을 알게 됐나 (재사용 가능한 사실) | 이 라이브러리는 초기화 순서가 강제된다 |

case는 사건 기록이라 시간순으로 쌓이고, fact는 주제별로 갱신됩니다.

### 저장 위치를 성격에 따라 나눈다

이 프로젝트에서만 의미 있는 것과, 다른 프로젝트에서도 쓸모 있는 것이 다릅니다.

| 성격 | 소속 | 저장 |
|---|---|---|
| 이 프로젝트 코드·설정·관례 | 프로젝트 | 저장소 내부 |
| 도구·플랫폼 공통 (배포 인증서, 스토어 심사 등) | 도구 일반 | 사용자 홈 |
| 로컬 환경 (런타임 버전, 네트워크 등) | 내 환경 | 사용자 홈 |

**판정은 조치 내역에서 자동으로 도출합니다.** 저장소 파일이 변경됐으면 프로젝트 것이고, 변경 없이 외부 설정만 건드렸으면 프로젝트 밖 것입니다. 이 신호로 대부분이 갈리며, 애매한 경우에만 근거를 제시하고 한 번 묻습니다.

검색할 때는 **양쪽을 모두** 조회합니다. 지금 막힌 것이 프로젝트 문제일 수도, 환경 문제일 수도 있기 때문입니다.

### 방법론 개선은 반복 패턴일 때만, 승인 후에

같은 원인이 여러 번 반복되면 조사 방법론 자체를 개선할 수 있습니다. 다만 한 번 겪은 특수 사례를 방법론에 넣으면 그 문서가 오염됩니다.

```
"담당자가 설정 한 줄을 지웠다"        → case에만 기록
"이 서비스는 컨테이너로 구동된다"      → fact에 기록
"기동 실패 3건이 모두 설정 누락이었다"  → 방법론 개선 제안
```

제안은 변경 내용을 보여주고 승인을 받은 뒤에만 반영합니다. `skills/`는 사용자에게 배포되는 자산이므로, 한 사람의 경험이 다른 프로젝트의 방법론을 자동으로 바꾸면 안 됩니다.

- 라우팅 표·README·`docs/SKILLS.md`·테스트 목록 정합화

**참고 — 설계 착안**

경험을 사례·사실·절차로 나눠 축적하고 그중 일반화 가능한 것만 절차로 승격하는 구조는, 최근 공개된 자기개선형 에이전트(Nous Research의 Hermes)의 closed learning loop 개념을 참고했습니다. 다만 해당 구현은 에이전트가 자신의 스킬을 자유롭게 수정할 수 있는 반면, 이 저장소의 `skills/`는 배포 자산이므로 **승인 단계를 필수**로 두어 더 보수적으로 설계했습니다.
