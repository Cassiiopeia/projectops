🗒️ 설명
---

스킬이 자신의 파이썬 스크립트(`*_cli.py`)를 찾을 때 참조하는 설치 경로가 **Claude Code 한 곳(`~/.claude/plugins/cache/...`)으로 하드코딩**되어 있습니다.

그런데 이 프로젝트는 **4개 하네스**에 배포됩니다. 레포 루트에 각 하네스용 매니페스트(`.claude-plugin/`, `.codex-plugin/`, `.agents/plugins/`)가 모두 존재하고, `harness/` 폴더까지 갖추고 있습니다. 그런데 정작 스킬이 스크립트를 찾는 코드는 Claude Code 경로만 봅니다.

결과적으로 **Codex, Gemini, pi 사용자는 스크립트를 전혀 찾지 못합니다.** 세 하네스에서는 캐시 탐색이 항상 빈 값이 되고, 뒤에 붙은 프로젝트 루트 폴백에만 의존하게 됩니다. 그런데 사용자 프로젝트에는 `skills/` 폴더가 없으므로(통합 시 제외 대상) 폴백도 실패합니다. 즉 **이 저장소 안에서만 우연히 동작하고, 실제 사용자 환경에서는 세 하네스 모두 스킬이 동작하지 않습니다.**

`#524`에서 탐색 순서를 "로컬 우선, 캐시 폴백"으로 바꾸면서 이 문제가 가려졌습니다. 이 저장소에는 `skills/`가 실재하므로 로컬이 먼저 잡혀 정상 동작처럼 보이지만, 사용자 환경에서는 로컬이 없어 캐시로 넘어가고 거기서 Claude Code 외 하네스가 탈락합니다.

🔄 재현 방법
---

1. Codex, Gemini, pi 중 하나에 projectops 플러그인을 설치한다
2. `skills/` 폴더가 없는 일반 프로젝트(템플릿으로 통합한 사용자 레포)로 이동한다
3. 스크립트 호출이 필요한 스킬을 실행한다 (예: 이슈 조회, 보고서 경로 계산)
4. 로컬 경로에 `skills/`가 없고 Claude Code 캐시도 없으므로 `cd` 대상이 빈 값이 되어 실패한다

📸 참고 자료
---

**하네스별 실제 설치 경로 (로컬 실측)**

| 하네스 | 실제 설치 경로 | 버전 계층 | 현재 탐색 대상 |
|---|---|---|---|
| Claude Code | `~/.claude/plugins/cache/{마켓}/{이름}/{버전}/skills/` | 있음 | 포함 |
| Codex | `~/.codex/plugins/cache/{마켓}/{이름}/{버전}/skills/` | 있음 | **누락** |
| Gemini | `~/.gemini/extensions/{이름}/skills/` | **없음** | **누락** |
| pi | `~/.pi/agent/git/github.com/{owner}/{repo}/skills/` | **없음** | **누락** |

- Codex는 Claude Code와 계층 구조가 동일하여 루트 경로만 추가하면 됩니다.
- Gemini와 pi는 버전 계층이 없어 `sort -V | tail -1`로 최신 버전을 고르는 현재 방식이 적용되지 않습니다. 글롭 패턴 자체가 달라야 합니다.
- 실측 시점에 pi에는 이 프로젝트가 실제로 설치되어 있었습니다 (v4.2.35). 즉 가상의 상황이 아니라 이미 사용 중인 경로입니다.

**참고 — 왜 별도 공용 스크립트로 빼지 않는가**

경로 해석 로직을 공용 스크립트 파일 하나로 분리하는 방안을 검토했으나, 그 공용 스크립트 자체를 찾으려면 결국 동일한 다중 경로 글롭이 필요해 순환이 됩니다. 축소 효과가 없으므로 `ls -d`에 여러 패턴을 한 번에 전달하는 방식이 적절합니다. 파일이 늘지 않고 기존의 self-contained 원칙도 유지됩니다.

**함께 확인된 결함 — 버전 선택이 경로 문자열 정렬에 좌우됨**

현재 코드는 후보 경로를 `sort -V | tail -1`로 정렬해 최신 버전을 고릅니다. 그런데 이 정렬 대상은 버전 문자열이 아니라 **경로 전체**입니다. 후보가 한 하네스 안에만 있을 때는 접두사가 같아 우연히 버전순이 되지만, **여러 하네스가 섞이면 하네스 루트 이름이 먼저 비교되어 버전과 무관한 항목이 선택됩니다.**

실측한 결과입니다. 네 패턴을 동시에 조회하면 다음이 잡혔습니다.

```
~/.claude/plugins/cache/projectops-marketplace/projectops/4.2.14/skills
   ... (중략, 4.2.35까지 8개)
~/.claude/plugins/cache/projectops-marketplace/projectops/4.2.35/skills
~/.pi/agent/git/github.com/Cassiiopeia/projectops/skills
```

`.pi`가 `.claude`보다 뒤이므로 `tail -1`은 항상 pi 설치본을 고릅니다. Claude Code에 더 최신 버전이 있어도 무시됩니다. 즉 다중 하네스를 지원하면 이 정렬 방식은 그대로 쓸 수 없습니다.

**참고 — 다중 패턴 동시 조회는 정상 동작함**

`ls -d`에 네 패턴을 한 번에 전달하는 방식은 실측에서 정상 동작했습니다. 설치되지 않은 하네스의 패턴은 매칭 실패로 조용히 제외되며(`2>/dev/null`), 나머지 결과에 영향을 주지 않았습니다. 위 실측에서 Codex와 Gemini는 해당 플러그인이 설치돼 있지 않아 자동으로 빠졌습니다.

✅ 예상 동작
---

- Claude Code, Codex, Gemini, pi **네 하네스 모두**에서 설치된 스크립트를 찾을 수 있어야 합니다
- 어느 하네스에 설치되어 있는지를 **실행 시점에 실제 파일 시스템을 보고 판별**해야 합니다. 특정 하네스를 가정하거나, 어느 하네스에서 실행 중인지 미리 알고 있다고 전제하지 않아야 합니다
- 후보가 여러 개일 때 **실제 버전을 기준으로** 선택해야 합니다. 경로 문자열 정렬에 의존하면 하네스 루트 이름이 버전보다 먼저 비교되어 잘못된 항목이 선택됩니다 (위 참고 자료의 실측 참조)
- 버전 계층이 없는 하네스(Gemini, pi)에서도 정상적으로 경로가 잡혀야 합니다
- 어느 하네스에서도 찾지 못한 경우 조용히 실패하지 않고, 특정 하네스에 종속되지 않은 중립적인 안내가 나와야 합니다
- 탐색 규칙이 15개 파일에서 제각각이지 않고 동일한 형태를 유지해야 합니다
- 새 하네스가 추가될 때 수정 지점이 명확해야 합니다
