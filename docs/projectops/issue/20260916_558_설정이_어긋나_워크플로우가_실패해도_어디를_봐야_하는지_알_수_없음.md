📝 현재 문제점
---

통합을 마친 뒤 워크플로우가 실패하면, 사용자는 **어디를 봐야 하는지 알 방법이 없다.**
Actions 로그는 증상만 보여주고 원인은 대개 저장소 설정에 있다.

실제 사례가 있다. 릴리스 후속 워크플로우를 자동 실행하는 기능이 저장소 권한 설정 때문에
전량 실패했는데(#555), 로그에는 `HTTP 403 Forbidden`만 찍혔다. 그 403이 "저장소
Actions 권한이 읽기 전용"이라는 뜻임을 알아내려면 GitHub 설정 화면 구조를 이미 알고
있어야 한다.

비슷하게 사용자가 막히는 지점들:

- 워크플로우 권한이 읽기 전용이라 자동 커밋·태그·트리거가 전부 실패
- 필요한 Secret이 등록되지 않아 배포 단계에서만 실패
- 병합 방식(merge commit) 설정이 꺼져 있어 릴리스 자동 머지가 실패
- 자동으로 채워져야 할 값이 치환되지 않은 채 남아 배포 시점에 엉뚱하게 실패

이 중 상당수는 **설치 직후에 이미 알 수 있는 사실**이다. 설치 후 검증(#549)이 미치환 값과
필요 Secret 목록을 뽑아내지만, 그건 통합을 다시 돌려야만 볼 수 있고 저장소 설정은 보지 않는다.

🛠️ 해결 방안 / 제안 기능
---

**언제든 실행할 수 있는 진단 명령을 추가한다.** 파일을 건드리지 않고 읽기만 한다.

**점검 항목**

| 구분 | 항목 | 무엇을 위한 것인지 |
|---|---|---|
| 로컬 | 통합 상태 | 이 폴더에 템플릿이 설치되어 있는가, 어느 버전인가 |
| 로컬 | 설치된 워크플로우 | 몇 개가 설치되어 있는가 |
| 로컬 | 치환되지 않은 값 | 배포 시점에 실패할 자리가 남아 있는가 |
| 로컬 | 필요한 Secret | 이 저장소가 실제로 요구하는 값은 무엇인가 |
| 로컬 | 업데이트 기준점 | 다음 업데이트가 사용자 수정을 구분할 수 있는가 |
| 원격 | 워크플로우 권한 | 자동 커밋·태그·후속 실행이 가능한가 |
| 원격 | Secret 등록 여부 | 필요한 값이 실제로 등록되어 있는가 |
| 원격 | 병합 방식 | 릴리스 자동 머지가 가능한가 |

로컬 항목은 네트워크 없이 동작한다. 원격 항목은 토큰이 있을 때만 점검하고, 없으면 그 사실을
알린 뒤 로컬 결과만 보여준다. **토큰이 없다고 실패시키지 않는다.**

**출력 원칙**

- 항목 이름 옆에 **"무엇을 위한 설정인지"**를 병기한다. 이름만으로는 그것이 자기 작업 흐름의
  무엇을 담당하는지 알 수 없다.
- 도구가 "고쳐야 한다"고 판정하지 않는다. **발견한 사실만 진술**하고 그것이 자신에게 문제인지는
  사용자가 판단한다. 쓰지 않는 워크플로우의 Secret은 등록할 이유가 없다.
- 문제 항목만 **현상 → 영향 → 조치** 순으로 펼치고, 정상 항목은 한 줄로 압축한다.
- GitHub 설정 화면에 실제로 표시되는 문자열은 번역하지 않는다. 번역하면 설명은 읽히지만
  정작 화면에서 그 항목을 찾지 못한다.

**재사용**

치환되지 않은 값과 필요 Secret 수집은 설치 후 검증(#549)이 이미 하는 일이다. 같은 모듈을
호출한다 — 두 곳에 따로 두면 판정 기준이 갈라진다.

⚙️ 작업 내용
---

- 진단 명령 신설 (읽기 전용, 파일 변경 없음)

- 원격 점검 항목 구현 (토큰이 있을 때만, 없으면 안내 후 로컬만)
- 출력 렌더러 (문제만 펼치고 정상은 압축)
- CLI 모드·도움말 등록
- 판정·렌더 회귀 테스트
