📝 현재 문제점
---

PAT 없이도 릴리스가 완주하도록 도입한 후속 워크플로우 트리거(#551)가 **실제 릴리스에서
전부 실패**했다. v4.4.0 릴리스 로그:

```
⚠️ 트리거 실패: PROJECT-COMMON-README-VERSION-UPDATE.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-CI.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-NPM-PUBLISH.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-PLUGIN-VERSION-SYNC.yaml (HTTP 403 Forbidden)
0개 트리거 / 실패 4개 / 깨울 수 없음 0개
```

**문제 1 — 권한 부족**

`workflow_dispatch` API 호출에는 `actions: write` 권한이 필요한데 릴리스 워크플로우의
권한 선언에 없다. 탐색·판정·호출까지 전부 정상 동작했지만 마지막 API에서 막혔다.

이번 릴리스는 이 저장소에 PAT가 있어 다른 단계가 PAT로 push한 덕에 후속 워크플로우가
`push` 이벤트로 정상 실행됐다. 즉 **실질 피해는 없었지만, PAT가 없는 저장소에서는 이
경로가 유일한 수단이므로 완전히 무용지물이다.** #551이 노렸던 효과가 그대로 사라진다.

**문제 2 — 발동 조건이 실제와 어긋남**

현재 조건은 "PAT로 머지하지 않았으면 깨운다"이다. 그런데 머지는 기본 토큰 1차 →
PAT 2차 구조라, **PAT가 있는 저장소에서도 1차가 성공하면 조건이 참**이 된다.

이번에 드러났듯 PAT가 있으면 다른 단계(브랜치 최신화 등)가 PAT로 push하므로 후속은 이미
`push`로 트리거된다. 권한을 고치면 거기에 dispatch까지 더해져 **같은 워크플로우가 두 번
돈다.** 대상 워크플로우 대부분이 멱등이라 사고는 아니지만, 릴리스마다 불필요한 실행이
쌓이고 로그를 읽기 어렵게 만든다.

🛠️ 해결 방안 / 제안 기능
---

**1. 권한 추가**

릴리스 워크플로우 권한 선언에 `actions: write`를 추가한다. 이 권한은 워크플로우 실행을
트리거하는 데만 쓰이며, 저장소 콘텐츠 권한과는 별개다.

**2. 발동 조건을 "PAT 부재"로 교정**

"PAT로 머지했는가"가 아니라 **"이 저장소에 PAT가 등록되어 있는가"**를 기준으로 삼는다.
PAT가 있으면 어떤 경로로든 push가 PAT 신원으로 나가 후속이 정상 트리거되므로 dispatch가
불필요하다. 머지 단계가 이미 PAT 존재 여부를 계산하고 있으므로 그 값을 내보내 쓴다.

정리하면:

| PAT 등록 | 후속 트리거 방식 |
|---|---|
| 있음 | push 이벤트 (기존 경로) — dispatch 건너뜀 |
| 없음 | dispatch로 직접 깨움 |

**3. 실패를 눈에 띄게**

지금은 실패해도 릴리스를 막지 않도록 조용히 넘어간다(의도된 설계). 다만 **PAT가 없어
dispatch가 유일한 수단인 상황에서 전부 실패하면 후속이 통째로 누락**되므로, 그 경우에는
릴리스 PR에 알림을 남겨 사용자가 인지하게 한다.

- 머지 단계가 PAT 존재 여부를 출력하도록 수정, 트리거 단계 조건 교체
- dispatch 전량 실패 시 릴리스 PR 알림 추가
- 조건 분기 회귀 테스트
