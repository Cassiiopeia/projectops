# 후속 워크플로우 트리거가 권한 부족으로 전부 실패하고 PAT 보유 레포에서는 중복 실행을 유발함

## 개요

#551에서 도입한 후속 워크플로우 트리거가 **실제 릴리스(v4.4.0)에서 전량 실패**했다.
`HTTP 403 Forbidden` — `workflow_dispatch` API에 필요한 `actions: write` 권한이 없었다.

같은 로그를 분석하다 **발동 조건 자체가 실제와 어긋나 있다**는 것도 드러났다. 둘 다 고쳤다.

단위 테스트·로컬 실측으로는 잡히지 않는 종류였다. 실제 GitHub Actions 환경에서 돌려봐야만
드러나는 문제다.

## 발견 경로

v4.4.0 릴리스 로그:

```
⚠️ 트리거 실패: PROJECT-COMMON-README-VERSION-UPDATE.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-CI.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-NPM-PUBLISH.yaml (HTTP 403 Forbidden)
⚠️ 트리거 실패: PROJECT-TEMPLATE-PLUGIN-VERSION-SYNC.yaml (HTTP 403 Forbidden)
0개 트리거 / 실패 4개 / 깨울 수 없음 0개
```

탐색·제외 판정·API 호출까지 전부 설계대로 동작했고 **마지막 권한에서만 막혔다.**

## 문제 1 — 권한 부족

`workflow_dispatch` API 호출에는 `actions: write`가 필요한데 릴리스 워크플로우의 권한
선언에 없었다.

이번 릴리스는 이 저장소에 PAT가 있어 다른 단계가 PAT로 push한 덕에 후속 워크플로우가
`push` 이벤트로 정상 실행됐다(`event=push`, 전부 success). **실질 피해는 없었지만,
PAT가 없는 저장소에서는 dispatch가 유일한 수단이므로 #551의 효과가 통째로 사라진다.**

## 문제 2 — 발동 조건이 실제와 어긋남

종전 조건은 "PAT로 머지하지 않았으면 깨운다"였다. 그런데 머지는 **기본 토큰 1차 → PAT
2차** 구조라, PAT가 있는 저장소에서도 1차가 성공하면 조건이 참이 된다.

이번에 드러났듯 **PAT가 있으면 다른 단계(브랜치 최신화 등)의 push가 PAT 신원으로 나가
후속이 이미 트리거된다.** 권한만 고치면 거기에 dispatch까지 더해져 같은 워크플로우가 두 번
돈다. 대상 대부분이 멱등이라 사고는 아니지만, 릴리스마다 불필요한 실행이 쌓이고 로그가
읽기 어려워진다.

판단 기준을 **"PAT가 등록되어 있는가"**로 바꿨다.

| PAT 등록 | 후속 트리거 방식 |
|---|---|
| 있음 | push 이벤트 (기존 경로) — dispatch 건너뜀 |
| 없음 | dispatch로 직접 깨움 |

## 변경 사항

- `PROJECT-COMMON-RELEASE-CHANGELOG.yaml` (루트·공통 원본): 권한에 `actions: write` 추가,
  머지 단계가 `pat_available`을 출력하도록 수정, 트리거 단계 조건 교체, 알림용 PR 번호 전달.
- `.github/scripts/dispatch_downstream.py`: 전량 실패 시 릴리스 PR에 알림(`_notify_pr`).
- `.github/scripts/test/test_dispatch_downstream.py`: 알림 분기 2케이스 추가 (총 15).

## 주요 구현 내용

### 전량 실패를 조용히 넘기지 않는다

#551의 설계는 "dispatch 실패가 릴리스를 막아선 안 된다"였고 그 자체는 옳다. 하지만 이번처럼
**하나도 못 깨운 경우**는 다르다. PAT가 없는 저장소에서 후속이 통째로 누락되는데 로그만
남기면 아무도 모른 채 지나간다.

하나라도 성공하면 알리지 않는다 — 알림은 "후속이 통째로 빠진" 상황 전용이다. 알림 본문에는
실패 워크플로우 목록과 함께 확인할 것(저장소 Actions 권한 설정, 수동 실행 방법)을 넣었다.

알림 실패 자체도 릴리스를 막지 않는다.

## 주의사항

### 이 수정도 다음 릴리스부터 적용된다

`pull_request_target`은 base 브랜치(main)의 워크플로우 파일로 실행된다. 이번 수정은 main에
머지된 **다음 릴리스**부터 효력이 생긴다. 그때 dispatch가 403 없이 도는지 확인해야 한다.

다만 이 저장소는 PAT가 있어 새 조건에서는 **dispatch가 아예 건너뛰어진다.** 즉
`actions: write` 수정의 실효는 **PAT가 없는 저장소에서만 검증 가능**하다. 이 레포에서
확인할 수 있는 것은 "조건이 올바로 작동해 dispatch를 건너뛰는가"까지다.

### 권한 추가의 범위

`actions: write`는 워크플로우 실행을 트리거·취소하는 권한이다. 저장소 콘텐츠 권한과 별개이며,
이 워크플로우는 이미 `contents: write`를 갖고 있어 권한 수준이 실질적으로 올라가지는 않는다.

### 교훈 — 단위 테스트가 잡지 못하는 층이 있다

`scan`의 탐색·제외 규칙은 13개 테스트로 고정돼 있었고 전부 통과했다. 로컬에서 실제 레포를
스캔해 targets 4개를 확인하기도 했다. **그럼에도 실제로는 한 건도 트리거되지 않았다.**

함수 단위 검증과 "실제 환경에서 끝까지 도는가"는 다른 층이다. 워크플로우 권한·이벤트 컨텍스트·
API 인증은 후자에서만 드러난다. 이 프로젝트에서 반복해서 확인되는 패턴이다(#546도 같았다).
