# 설정이 어긋나 워크플로우가 실패해도 어디를 봐야 하는지 알 수 없음

## 개요

통합 후 워크플로우가 실패할 때 원인은 대개 저장소 설정에 있는데, Actions 로그는 증상만
보여준다. **언제든 실행할 수 있는 읽기 전용 진단 명령**(`--mode doctor`)을 추가했다.

```bash
npx projectops --mode doctor                       # 로컬 점검
GITHUB_TOKEN=ghp_... npx projectops --mode doctor  # 저장소 설정까지
```

착수 근거는 실제 사고다. #555에서 후속 워크플로우 트리거가 전량 `HTTP 403`으로 실패했는데,
그 403이 무엇을 뜻하는지 알아내려면 GitHub 설정 구조를 이미 알고 있어야 했다.

## 점검 항목

| 구분 | 항목 | 무엇을 위한 것인지 |
|---|---|---|
| 로컬 | 통합 상태 | 템플릿이 설치되어 있는가, 어느 버전인가 |
| 로컬 | 설치된 워크플로우 | 몇 개가 도는가 |
| 로컬 | 치환되지 않은 값 | 배포 시점에 실패할 자리가 있는가 |
| 로컬 | 필요한 Secret | 이 저장소가 실제로 요구하는 값 |
| 로컬 | **워크플로우 권한 선언** | 다른 워크플로우를 실행할 권한이 선언돼 있는가 |
| 로컬 | 업데이트 기준점 | 다음 업데이트가 내 수정을 구분할 수 있는가 |
| 원격 | Workflow permissions | 자동 커밋·태그·후속 실행이 가능한가 |
| 원격 | merge commit 허용 | 릴리스 자동 머지가 가능한가 |
| 원격 | Secret 등록 여부 | 필요한 값이 실제로 등록돼 있는가 |

## 주요 구현 내용

### 저장소 설정과 워크플로우 선언은 다른 층이다 (핵심 발견)

구현 중 실측으로 드러난 사실이다. **이 저장소는 Workflow permissions가
`Read and write permissions`인데도 #555에서 403이 났다.**

| 층 | 의미 |
|---|---|
| 저장소 설정 (Settings > Actions) | 워크플로우가 요청할 수 있는 **최대 범위** |
| 워크플로우 파일의 `permissions:` 블록 | 실제로 **요청한 범위** |

최대 범위가 열려 있어도 선언이 빠지면 API는 403을 준다. 따라서 **저장소 설정만 점검하는
진단은 #555를 잡지 못한다.** 워크플로우 파일의 선언까지 보는 항목을 추가했다.

다른 워크플로우를 깨우는 파일(`dispatch_downstream.py` 호출)을 찾아 `permissions` 블록에
`actions: write`가 있는지 확인한다. **#555 수정 전 상태를 재현해 실제로 잡히는지 검증했다.**

```
⚠️ 워크플로우 권한 선언 — 다른 워크플로우를 실행할 권한: 1건 누락
       PROJECT-COMMON-RELEASE-CHANGELOG.yaml
     다른 워크플로우를 실행하는데 permissions에 'actions: write'가 없습니다.
     저장소 설정이 Read and write여도 이 선언이 없으면 API가 403을 반환합니다.
```

### 판정하지 않고 사실만 진술한다

도구가 "고쳐야 한다"고 단정하지 않는다. 쓰지 않는 워크플로우의 Secret은 등록할 이유가 없고,
그것이 자신에게 문제인지는 사용자가 판단한다. 필요한 Secret 목록을 `WARN`이 아니라 `INFO`로
두는 이유다.

### GitHub 화면 문자열은 번역하지 않는다

`Read and write permissions`, `Allow merge commits` 같은 값은 원문 그대로 쓴다. 번역하면
설명은 읽히지만 정작 설정 화면에서 그 항목을 찾지 못한다.

### 검증 모듈을 재사용한다

치환 누락과 필요 Secret 수집은 설치 후 검증(#549)이 이미 하는 일이다. 같은 모듈을 호출한다 —
두 곳에 따로 두면 판정 기준이 갈라진다.

### 토큰이 없어도 실패하지 않는다

원격 점검은 `GITHUB_TOKEN`이 있을 때만 한다. 없으면 그 사실과 사용법을 알린 뒤 로컬 결과만
보여준다. 로컬 점검만으로도 흔한 사고(치환 실패·Secret 누락·권한 선언 누락)는 잡힌다.

진단은 실패가 아니므로 살펴볼 항목이 있어도 **exit code 0**으로 끝낸다. CI에서 게이트로 쓰려
한다면 별도 설계가 필요하다.

## 주의사항

### 권한 선언 점검은 dispatch 호출만 본다

현재는 "다른 워크플로우를 깨우는가"만 판정 기준으로 쓴다. 다른 권한(`packages: write` 등)이
필요한 워크플로우가 생기면 같은 자리에 규칙을 추가해야 한다. 일반화된 권한 추론은 하지 않는다 —
워크플로우가 실제로 무엇을 하는지는 정적 분석으로 정확히 알 수 없다.

### 원격 점검에 필요한 토큰 권한

저장소 설정·Secret 목록 조회에는 관리 권한이 필요하다. 권한이 모자라면 실패로 처리하지 않고
"조회 권한 없음"으로 알린 뒤 직접 확인할 경로를 안내한다.

### gh CLI를 쓰지 않는다

참조 구현(`project-auto-wizard`)의 doctor는 gh CLI에 위임하지만, 이 레포의 마법사는 git 외에
외부 CLI를 쓰지 않는다. 그 방침을 유지해 `fetch`로 직접 호출한다.
