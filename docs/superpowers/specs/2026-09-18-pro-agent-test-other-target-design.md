# pro-agent-test — 네 번째 타겟 `other` 와 "남의 환경" 축

## 왜 필요한가

테스트 앱 빌드가 두 번 연속 깨졌다.

| 이슈 | 무엇이 | 왜 여기선 안 터졌나 |
| --- | --- | --- |
| #595 | 워크플로에 `permissions` 없음 | projectops 는 기본 권한이 `write`. elum 은 신규 레포라 `read` |
| #597 | if 블록 안 heredoc 종료자 들여쓰기 | 이슈 댓글로 트리거할 때만 타는 경로. 여기선 안 밟음 |

둘 다 **스킬로 잡을 방법이 없었고**, 사용자가 다른 레포(elum)에서 진짜 빌드를 돌려서야 드러났다.

같은 세션에서 나온 나머지도 모양이 같다.

| 무엇이 | 왜 안 걸렸나 |
| --- | --- |
| `_require_playwright` 안내 문구가 옛 키를 봄 | 내 맥엔 Playwright 가 있어 그 테스트가 **항상 skip** |
| 테스트 코드 921줄이 사용자 홈으로 복사됨 | 복사 **결과**를 아무도 열어보지 않음 |
| `note`·`scenario init` 5종 크래시 | 테스트가 `--help` 에 이름만 확인, **실행 안 함** |

전부 **"내 환경에서는 통과하는데 남의 환경에서 터진다"** 다.

> **해결해야 할 것은 "CI 를 돌리는 기계가 없다" 가 아니다.**
> **"내 환경에서만 통과하는 것을 알아채지 못한다" 다.**

## 무엇을 만드나

### 1. 네 번째 타겟 `other`

```python
TARGETS = ("app", "web", "server", "other")
```

`other` = 앱·웹·서버가 아닌 **모든 것.** CI 워크플로·CLI 툴·라이브러리·템플릿·배치·마이그레이션 스크립트.

**종류를 열거하지 않는다.** `pipeline`·`cli`·`library` 로 나누면 목록에 없는 것은 또 못 한다. 프로젝트를 미리 정해둔 틀에 끼워 맞추는 것은 #589 에서 걷어낸 병이다.

| 타겟 | 조작 수단 | 판정 근거 |
| --- | --- | --- |
| `app` | adb 탭 | 화면 + 기기 상태 + 서버 |
| `web` | Playwright | 화면 + 콘솔 + 서버 |
| `server` | HTTP | 응답 + DB + 로그 |
| **`other`** | **명령을 돌린다** | **종료코드 · 출력 · 만들어진 것 · 다시 돌렸을 때** |

`other` 에서는 **무엇을 밟을지가 정해져 있지 않다.** agent 가 "이 프로젝트의 산출물이 무엇인가" 부터 정한다. 스킬은 그 판단을 돕고, 판단이 끝난 뒤의 실행과 관찰을 맡는다.

### 2. `other run` — agent 가 놓치는 것만 기계가 본다

```
other run --root {ROOT} --command "{명령}"
          [--cwd {디렉터리}]      # 기본: --root
          [--expect-exit N]
          [--expect-output "{문자열}"]
          [--watch {경로} ...]    # 실행 전후 파일 변화를 본다
          [--twice]               # 두 번 돌려 같은 결과인지
          [--env K=V ...]
          [--timeout N]           # 기본 120
```

**판정 조건은 전부 선택이다.** 주지 않으면 그냥 돌리고 결과를 돌려준다 — 읽고 판단하는 것은 agent 의 일이다. 조건을 주면 기계가 대신 대조해 준다.

출력:

```json
{
  "ok": true,
  "command": "npx projectops --type spring --yes",
  "exit_code": 0,
  "elapsed_ms": 4210,
  "stdout_tail": "...",
  "stderr_tail": "...",
  "files": {
    "created": [".github/workflows/PROJECT-COMMON-VERSION-CONTROL.yaml"],
    "modified": ["version.yml"],
    "deleted": []
  },
  "second_run": {"exit_code": 0, "same_files": true, "same_stdout": false},
  "problems": ["두 번째 실행에서 stdout 이 달랐다"],
  "summary": "...",
  "next": "..."
}
```

기계가 담당하는 것은 셋뿐이다.

| 보는 것 | 왜 사람이 못 보나 |
| --- | --- |
| **실행 전후 파일 변화** | 출력만 보고 **부작용을 보지 않는다.** 테스트 921줄 유출이 이 눈이 없어 생겼다 |
| **두 번 돌렸을 때 같은가** | 멱등은 중요한데 손으로는 거의 해보지 않는다 |
| 종료코드·출력·소요시간 | 기본 |

**`--watch` 는 명시한 경로만 본다.** 레포 전체를 뜨면 `node_modules`·`.git` 이 섞여 느리고 쓸모없다. 주지 않으면 파일 관찰을 하지 않는다.

**타임아웃은 기본값이 있다.** 없으면 매달린 명령에 세션이 묶인다.

### 3. 시나리오 — `expect_absent` 를 더한다

```python
_EXPECT_KEYS["other"] = ("expect_exit", "expect_output", "expect_file", "expect_absent")
```

```json
{
  "target": "other",
  "name": "npx CLI 가 남의 프로젝트에서 도는가",
  "steps": [
    {"screen": "도움말", "do": "npx projectops --help",
     "expect_exit": 0, "expect_output": "projectops"},
    {"screen": "통합", "do": "npx projectops --type spring --yes",
     "expect_file": ".github/workflows/PROJECT-COMMON-VERSION-CONTROL.yaml",
     "expect_absent": "skills/pro-agent-test/tests"}
  ]
}
```

`expect_absent` 가 핵심이다. 지금까지 스킬은 **"있어야 할 것"만** 봤다. 테스트 코드 유출·임시 파일 잔존·지워졌어야 할 구 파일은 전부 **"없어야 할 것"** 쪽이라 판정 근거가 아예 없었다.

`screen` 은 `other` 에서 "단계 이름"으로 읽는다. 기존 필수 키를 재사용해 스키마를 갈라놓지 않는다.

**판정 의미를 애매하게 두지 않는다.**

| 키 | 통과 조건 | 기준 경로 |
| --- | --- | --- |
| `expect_exit` | 종료코드가 정확히 같다 | — |
| `expect_output` | stdout+stderr 에 그 문자열이 **들어 있다**(부분 일치) | — |
| `expect_file` | 그 경로가 **실행 뒤에 존재한다** | `--cwd` 기준 (없으면 `--root`) |
| `expect_absent` | 그 경로가 **실행 뒤에 없다** | 〃 |

부분 일치로 두는 이유는 `expect_url` 과 같다 — 전체 일치를 요구하면 출력 문구가 한 글자만 바뀌어도 시나리오가 깨진다.

`expect_file`·`expect_absent` 는 **존재 여부**만 본다. 변화가 아니다. "실행 전에도 있었다" 를 구분해야 하면 `--watch` 의 `files.created` 를 본다.

### 4. 새 축 — 남의 환경에서 처음 돌 때 (Phase 4.7)

**타겟을 가리지 않는다.** 앱도 "내 폰에선 되는데" 가 있고, 서버도 "내 로컬 DB 에선 되는데" 가 있다.

| 렌즈 | 묻는 것 | 어떻게 밟나 | 이번에 걸렸다면 |
| --- | --- | --- | --- |
| **기본값** | 설정을 명시하지 않고 환경 기본값에 기대는가 | 기본값이 다른 환경을 만들어 돌린다 | #595 권한 |
| **설치물** | 내 기계에만 있는 것에 기대는가 | 그것을 숨기고 돌린다 | Playwright skip |
| **첫 상태** | 처음 쓰는 사람의 빈 상태에서 시작하는가 | 설정·기록을 지운 곳에서 돌린다 | 빈 config |
| **안 밟은 분기** | 조건이 맞아야만 타는 경로가 있는가 | 코드에서 분기를 세고 안 밟은 것을 밟는다 | #597 댓글 경로 |
| **결과물** | 만들어진 것을 눈으로 보았는가 | 산출물을 열어본다 | 테스트 921줄 유출 |

Phase 4.5(횡단·대칭·파급)와 나란히 둔다. 4.5 는 **"같은 성격의 다른 곳"**을 보고, 4.7 은 **"같은 것의 다른 환경"**을 본다.

### 5. `references/target-other.md`

- 이 프로젝트의 **산출물이 무엇인가** 부터 정한다 — 파일인가, 실행인가, 게시물인가, 파이프라인 결과인가
- 무엇을 "한 단계" 로 볼 것인가
- 판정 근거 고르는 법 (종료코드만 보지 않는다)
- CI 워크플로를 밟을 때 — `pro-github` 의 `actions` 서브커맨드와 엮는 법
- 되는 것 · 안 되는 것

### 6. `detect` 에서의 취급

`other` 는 **마커로 감지하지 않는다.** 모든 레포가 해당될 수 있어 항상 나오면 노이즈다.

- `--target other` 로 직접 지정
- `note target --targets other --why "..."` 로 agent 가 확인해 적는다
- `confirm` 안내에 "밟을 것이 앱·웹·서버가 아니면 `other`" 한 줄을 더한다

## 하지 않는 것

- **CI 를 트리거하는 전용 기계를 만들지 않는다.** `other run` 이 `gh`/`github_cli.py` 를 부르면 되고, run 추적·로그는 `pro-github` 의 `actions` 가 이미 한다. 같은 일을 두 곳에 두면 어긋난다.
- **종류별 하위 타입(`pipeline`·`cli`·`library`)을 두지 않는다.** 확장성이 사라진다.
- **`--watch` 기본값을 레포 전체로 두지 않는다.** 느리고 노이즈가 많다.

## 테스트

| 무엇을 | 어떻게 |
| --- | --- |
| `other run` 이 실제로 돈다 | 임시 디렉터리에서 파일을 만드는 명령을 돌려 `files.created` 에 잡히는지 |
| 파일 변화 관찰 | 생성·수정·삭제 세 가지를 각각 |
| `--twice` 멱등 판정 | 같은 결과를 내는 명령과 매번 다른 명령 두 가지로 |
| `--expect-*` 대조 | 통과·실패 양쪽 |
| `expect_absent` | 있으면 실패, 없으면 통과 |
| 시나리오 검증 | `other` 타겟에 기대 결과가 하나도 없으면 거부하는지 |
| 타임아웃 | 매달리는 명령이 제한 시간에 끊기는지 |

**환경에 따라 건너뛰는 테스트를 만들지 않는다** (#591 에서 얻은 것). 도구가 필요하면 없는 상태를 테스트가 직접 만든다.

## 열린 것

- **CI 트리거를 스킬이 직접 할 것인가** 는 이번 범위 밖에 둔다. `other run` 으로 `github_cli.py` 를 부르는 것은 가능하지만, 러너 시간과 스토어 심사가 걸린 판단이라 사용자 승인 절차를 별도로 설계해야 한다.
- **기록의 팀 공유** 는 여전히 홈에만 쌓인다 (#591 에서 의도적으로 둔 것).
