# pro-design-brief — 시안보다 먼저 만든 화면의 디자인 요청서

> 상태: 설계 확정 · 작성 2026-09-25 · 이슈 #634
> 선행: `2026-09-25-pro-launch-design.md` (캡처·렌더를 여기에 맡긴다)
> 실례: Twin-Fang/elum #419 (이 스킬이 할 일을 사람이 손으로 한 첫 사례)

## 1. 왜 만드나

요즘 개발 흐름은 **AI 가 먼저 화면을 만들고, 시안은 나중에 온다.** 또는 디자이너가 "어떻게 그려야 할지
모르겠다"고 한다. 그때 개발 쪽이 디자이너에게 넘기는 요청서가 매번 손으로 만들어진다.

2026-09-25 elum 에서 앱 버전 표시를 임시로 구현한 뒤 디자이너에게 보낸 #419 가 그 예다.
사람이 한 일을 풀어 보면 다음과 같다.

1. 실제 화면을 렌더해 캡처했다 (로그인 iOS·Android, 설정)
2. 배치 대안 4안, 설정 3안을 실제 컴포넌트로 렌더했다
3. 작은 글자를 4배 확대해 붙이고 비교 보드로 합쳤다
4. 이슈 본문에 "꼭 지킬 것", "개발 쪽 추천", "고르면 개발이 더 필요한 안"을 적었다
5. 이미지를 올리고 디자인 이슈를 등록해 디자이너에게 배정했다

이 스킬은 이 과정을 절차로 만든다. 그리고 사람이 빼먹은 것을 더한다. **디자이너는 보통 기본 화면만
그린다.** 목록이 있을 때만 그리고, 비었을 때·실패했을 때·글자가 길 때는 그리지 않는다.

### 이 스킬은 정답을 주지 않는다

디자이너에게 **생각할 재료**를 준다. 대안 · 문구 후보 · UI 요소 후보 · 엣지 상태를 넓게 펼친다.
개발 쪽 선호는 근거와 함께 한 줄만 적고, 보드 맨 위에 "전부 바꿔도 된다"를 박는다.

### 반면교사 — 산출물 없는 디자인 스킬은 지워졌다

projectops #535 에서 `design`, `design-analyze` 스킬이 **"산출물 실적이 없어서"** 삭제됐다.
이 스킬은 반드시 **디자이너가 받아 보는 결과물**(이미지가 든 이슈 / HTML 페이지 / md 폴더)로 끝난다.
"분석 결과를 채팅으로 말하기"로 끝나지 않는다.

## 2. 언제 쓰나 / 쓰지 않나

| 쓴다 | 쓰지 않는다 |
|---|---|
| 시안 없이 먼저 구현했다 → 시안 요청 | 시안이 있고 코드로 옮기는 중 → `pro-figma-verify` |
| 시안이 기본 화면만 있다 → 빠진 상태 요청 | 버그 찾기 → `pro-agent-test` |
| 디자이너가 방향을 못 잡는다 → 재료 제공 | 디자인 시스템을 새로 짠다 |
| 아직 구현 전이지만 방향을 같이 잡고 싶다 | |

트리거 발화 예: "디자인 요청해줘", "시안 요청 올려줘", "디자이너한테 보낼 거 만들어줘",
"이거 디자인 안 나왔는데 먼저 만들었어", "빈 화면이랑 에러 화면도 그려 달라고 해줘".

## 3. 흐름

```
0. 설정 판정 ─ 출력 방식 · 디자이너 · 게시 전 확인 (처음 한 번, 이후 자동)
1. 입력 파악 ─ 대화 맥락 우선 → 대상 화면·기능·관련 이슈
               구현 여부: 구현됨 / 일부 / 아직 없음
               사용자가 준 것: Figma 링크 · 이미지 · 없음
2. 상태 목록 ─ 이 화면이 가질 수 있는 상태를 뽑고 구현 여부를 표시
3. 캡처 ───── pro-launch: 코드 렌더 → 실기기·브라우저 → ASCII
4. 대안 ───── 배치안 · 문구 후보 · UI 요소 후보 · 꼭 지킬 것
5. 보드 ───── HTML 템플릿 하나 → PNG (출력 방식에 맞춰 담는다)
6. 게시 ───── 승인 게이트(A/B/C) → issue / html / markdown
```

**대화에 이미 있는 것은 다시 조사하지 않는다** (`approval-and-questions.md` §2). 구현 직후에 부르면
1~2단계는 대화에 거의 다 있다. 특히 "왜 이 자리를 골랐나"는 대화에만 있으니 반드시 살린다.

## 4. 단계별 명세

### 4.0 설정 판정

설정 파일(`{HOME}/.projectops/config/config.json`)에 **독립 섹션** `design_brief` 를 둔다.
GitHub 을 쓰지 않는 레포는 `github.repos[]` 에 없을 수 있어서 `github` 아래에 두지 않는다.

```json
"design_brief": {
  "destination": "issue",
  "auto_approve": false,
  "projects": [
    { "match": "Twin-Fang/elum", "destination": "issue", "designer": "yeramyyi", "auto_approve": true },
    { "match": "/Users/me/work/landing", "destination": "html", "designer": "김디자인" }
  ]
}
```

- `match` — GitHub `owner/repo` 또는 레포 절대경로. remote 가 GitHub 이 아니면 경로로 맞춘다.
- 해석 우선순위: `projects[]` 일치 항목 → 섹션 기본값 → 없으면 첫 실행 판정.

| 처음 정할 것 | 자동 판정 | 판정 안 되면 묻는다 |
|---|---|---|
| `destination` (`issue`/`html`/`markdown`) | remote 가 GitHub 이고 `github.repos[]` 에 있으면 `issue` 제안 | "이 레포는 디자인 요청서를 어떻게 받으세요?" |
| `designer` | `.github/ISSUE_TEMPLATE/*` 의 `디자인:` 줄, 최근 디자인 이슈 담당자 | "디자이너 GitHub 아이디(또는 이름)가 뭔가요?" |
| `auto_approve` | 없음 — 기본 수동 | 첫 게시 때 C 분기 |

규칙은 `approval-and-questions.md` · `config-rules.md` 를 따른다 — **한 번에 한 질문**, 권장안을 1번에,
**사용자에게 설정 키 이름·파일 경로를 보여주지 않는다**, "다음부턴 HTML 로 해줘" 같은 자연어로 바꾼다.
저장은 전체를 Read 한 뒤 해당 키만 바꿔 Write 한다.

`config-rules.md` §7 에 `design_brief` 스키마 표를 추가하고 `config.json.example` 에 예시를 넣는다.

### 4.1 입력 파악

| 사용자가 준 것 | 하는 일 |
|---|---|
| 없음 | 코드 · 캡처 · 대화만으로 만든다 (#419) |
| **Figma 링크** | `pro-figma-verify` 의 MCP 읽기 절차로 읽는다 (4.1.1) |
| 이미지 (스크린샷 · 참고 앱) | 보드 "참고" 칸에 넣고 무엇을 참고했는지 한 줄 적는다 |

#### 4.1.1 Figma 가 있을 때

MCP 읽기 규칙은 **`pro-figma-verify` 에 이미 있다** — 두 번 나눠 받기, 컴포넌트 섹션을 화면보다 먼저
보기, 참조로만 오는 스타일 복원, 한 문자열에 뭉친 그림자 풀기. 이 규칙을 공용 참조로 올리고(#630)
두 스킬이 같이 쓴다.

Figma 에서 얻는 것:

1. **시안에 그려진 상태 vs 빠진 상태** 빈틈 표 — figma-verify 의 "상태를 다 세었는가" 절차를 재사용.
   빠진 상태가 곧 요청 목록이 된다.
2. **토큰 · 컴포넌트** — 대안 목업을 시안 언어로 그린다 (색·글꼴·모서리).
3. **시안 export PNG** — 보드에 `시안 | 현재 구현 | 대안` 세 칸.
4. **시안끼리 어긋난 곳** — 상태 프레임마다 문구가 다른 경우 등. **고치지 않고 질문으로 올린다.**

### 4.2 상태 목록 — 디자이너가 안 그리는 화면을 찾는다

| 축 | 뽑는 곳 (agent 가 코드를 읽는다) | 예 |
|---|---|---|
| 데이터 | 비동기 분기 · 빈 값 검사 · 예외 처리 · 에러 코드 목록 | 0건 · 1건 · 많음 · 로딩 · 실패 · 부분 실패 |
| 입력 | 검증 · 최대 길이 | 빈 칸 · 너무 긴 이름 · 금지 문자 |
| 환경 | 권한 요청 · 네트워크 처리 | 권한 거부 · 오프라인 · 타임아웃 |
| 사람 | 역할 · 첫 사용 여부 | 역할별 화면 · 처음 · 재방문 |
| 표시 | 글자 크기 · 테마 · 폭 | 글자 200% · 다크 · 작은 폰 · 태블릿 · 데스크톱 |

- 상태마다 **구현됨 / 코드는 있는데 화면이 임시 / 미구현** 을 표시한다.
- **이 화면에 실제로 해당하는 축만** 넣는다. 억지로 채우지 않는다 (버전 표시에 "0건" 없음).
- 스크립트가 분기를 스캔하지 않는다. agent 가 코드를 읽고 목록을 적는다 (pro-launch §3 원칙 1).

### 4.3 캡처

`pro-launch` 를 스크립트로 부른다. 순서: 코드 렌더(`render run`) → 실기기·브라우저(`app shot` ·
`web shot` + `web route`) → ASCII.

- 캡처 자리는 `get-output-path --skill design-brief`.
- 현재 구현 × 상태별로 찍는다. 대안 목업도 **실제 컴포넌트로** 렌더한다 (HTML 로 다시 그리면 글꼴·간격이
  달라 디자이너가 헷갈린다 — #415 와 #419 의 차이).
- 작은 요소(버전 글자처럼)는 확대 조각을 함께 만든다.

### 4.4 대안 · 문구 · UI 요소 · 꼭 지킬 것

**① 배치 대안 — 모양이 아니라 축이 달라야 한다**

- 3~5안. 갈라지는 축: 위치 · 밀도 · 표현(글자·아이콘·배지) · 진입(그 자리·새 화면·시트).
- **항상 "현재 구현" 안과 "최소" 안을 포함한다.**
- 안마다 `장점 · 약점 · 개발 영향`. 개발 영향은 "이 안은 서버에 없는 값이 필요해 개발이 따로 든다" 같은 것.
- 추천은 근거와 함께 한 줄.

**② 문구 — AI 티와 레포 용어 규칙**

화면 문자열을 전부 뽑아 `현재 → 후보 2~3 → 이유` 표로 만든다.

| 짚는 것 | 예 |
|---|---|
| 번역투 · 딱딱함 | "~하실 수 있습니다", "~되었습니다" |
| 장황 · 반복 | 제목과 본문이 같은 말 |
| AI 문장부호 | em dash(—) · 가운뎃점(·) 남발 |
| 과장 | "혁신적인", "완벽한" |
| 레포 용어 규칙 위반 | 레포 CLAUDE.md · 디자인 원칙 문서의 용어표·말투 규칙 (예: elum "아이 → 이룸이", 해요체) |

- 레포 규칙은 **자동으로 읽는다**: 루트·모듈 `CLAUDE.md`, `docs/*design*`, 용어표.
- **법적 문구(약관·동의)는 "바꾸면 안 됨" 표시만** 하고 후보를 내지 않는다.
- 상태별 문구(빈 목록·실패 안내)가 없으면 **"문구 필요"** 로 표시한다.

**③ UI 요소 후보 — 데이터 모양에서 고른다**

| 데이터 모양 | 후보 |
|---|---|
| 하나 고르기 | 라디오 · 세그먼트 · 드롭다운 · 카드 선택 |
| 여러 개 고르기 | 체크박스 · 칩 · 토글 목록 |
| 긴 내용 | 아코디언 · 더보기 · 바텀시트 |
| 확인 · 알림 | 팝업 · 토스트 · 그 자리 안내 |
| 목록 | 리스트 · 그리드 · 카드 |

- **레포에 이미 있는 컴포넌트를 먼저** 쓴다. 없는 것은 "새 컴포넌트" 표시.
- 후보는 렌더하고, 안 되면 ASCII.

**④ 꼭 지킬 것 — 자동 수집**

브랜드 규격(예: Apple 로그인 버튼 문구 3종만 허용), 최소 터치 크기, 레포 디자인 원칙, 이미 합의된 예외
(예: elum #228 "코드·모드는 시안대로"). 출처를 함께 적는다.

### 4.5 보드

**HTML 템플릿 하나**로 조립하고, 헤드리스 브라우저(pro-launch 의 Chromium)로 PNG 를 뽑는다.
PIL 로 좌표를 계산해 합치던 #419 방식은 글자 배치를 여러 번 고쳐야 했다 (확대 영역 두 번 수정).

```
1 요약        무엇을 · 왜 · 지금 상태 · 꼭 지킬 것 · "정답이 아니다"
2 현재 구현   플랫폼별 실제 캡처
3 상태 격자   상태 × 구현 여부 (캡처 / ASCII / "문구 필요")
4 대안 비교   안별 캡처 · 확대 조각 · 장단점 · 개발 영향 · 추천 한 줄
5 문구표      현재 → 후보 → 이유 · 필요한 문구
6 UI 요소     데이터 모양별 후보
7 개발 영향   고른 안에 따라 따로 필요한 개발
(Figma 가 있으면 2·4 에 "시안" 칸, 빈틈 표를 3 에)
```

템플릿은 `skills/pro-design-brief/assets/board.html` + 데이터(JSON). 조립은 CLI `design_brief_cli.py board`.

- **주제별로 PNG 를 나눈다** (한 장에 다 넣으면 GitHub 에서 안 읽힌다). 한 장 폭 ≤ 3,400px.
- 안 이름은 A·B·C 로 통일하고 이슈 본문 설명과 같은 이름을 쓴다.

### 4.6 게시

| destination | 디자이너가 받는 것 | 방법 |
|---|---|---|
| `issue` | 이슈 본문 + PNG | `pro-github` 스크립트: `upload-image` → `create-issue` (디자인 템플릿 🖌️🎯📋💡🙋 섹션에 맞춘다), 담당자 = designer, 관련 구현 이슈 링크 |
| `html` | HTML 페이지 하나 (이미지 내장) | 보드 HTML 을 그대로 산출물 폴더에 저장. 탭으로 상태·문구 후보를 넘겨 본다 |
| `markdown` | md + PNG 폴더 | 산출물 폴더에 저장 |

**디자이너에게는 한 형식만 준다.** 둘 다 주면 어느 쪽을 볼지 헷갈린다.

게시 직전 승인 게이트는 `approval-and-questions.md` §4 의 A/B/C 를 그대로 쓴다. 이슈 제목은
레포 제목 규칙을 따른다 (예: elum `🎨[디자인][클라][설정] ...`). 구현 이슈가 있으면 서로 링크한다.

## 5. 스크립트 (design_brief_cli.py)

판단은 agent, 스크립트는 실행·기록 (pro-launch §3).

| 명령 | 하는 일 |
|---|---|
| `config show\|set` | `design_brief` 섹션 해석 결과 (일치 항목 · 출처) / 저장 |
| `get-output-path --title` | 산출물 자리 (`EVIDENCE_SKILLS` 에 `design-brief` 추가) |
| `board --data <json> --out <dir> [--png]` | 템플릿 조립 → HTML, `--png` 면 주제별 PNG. PNG 는 pro-launch 의 Chromium(`web setup` 으로 설치된 것)으로 찍는다 — 브라우저를 따로 설치하지 않는다 |
| `copy-lint --file <json>` | 문구 후보 표의 기계적 검사: em dash · 가운뎃점 · 금지어 목록(레포 설정에서 읽은 것) 위반 표시. **좋은 문구를 만들지는 않는다** — 그건 agent 몫 |
| `ascii --spec <json>` | 박스 문자 와이어 렌더 (폭 고정 · 한글 폭 보정) |

## 6. 실패 경로

| 상황 | 동작 |
|---|---|
| 브라우저 없음 | PNG 보드 대신 md 표 + 원본 캡처로 낸다, 사유를 요약에 적는다 |
| 렌더 실패 | 그 상태만 ASCII 로 대체하고 "렌더 실패" 표시 |
| 업로드 실패 | 로컬 산출물로 남기고 경로를 알려준다 |
| Figma 읽기 실패 (토큰 없음 등) | Figma 없이 진행하고 요약에 적는다 |
| 디자이너 모름 | 담당자 없이 등록하고 알린다 (설정은 다음에 묻는다) |
| 대상 레포에 흔적 | pro-launch `residue` 를 그대로 보고, 지우지 않는다 |
