# Note Mode

알아낸 것을 **AI 없이도 따라 할 수 있는 기록**으로 남기고, 막혔을 때 그것을 꺼내 쓴다.

## 이 스킬의 목적

기록의 독자는 **6개월 뒤의 누군가**다. 그 사람은 이 대화를 못 봤고, AI 도움 없이 터미널 앞에 앉아 있을 수도 있다.

그 사람이 이 문서만 보고 **같은 문제를 처음부터 끝까지 해결할 수 있어야 한다.** 이것이 유일한 품질 기준이다.

따라서:

- 명령어는 **복사해서 그대로 실행 가능**해야 한다 — 경로를 구체적으로, 축약하지 않고
- 각 명령이 **무엇을 확인하기 위한 것인지**와 **어떤 출력이 나오면 무슨 뜻인지**를 함께 적는다
- 되돌릴 수 없는 조치 앞에는 **백업 절차**를 먼저 둔다
- "이렇게 하면 된다"가 아니라 **왜 이 문제가 생겼고 왜 이 조치가 맞는지**를 적는다
- 증거 없이 원인을 단정하지 않는다. 불확실하면 `(추정)`이라고 표시한다

## 승인 게이트 · 시작 전 질문

`references/approval-and-questions.md`를 따른다. 다만 이 스킬은 **막혔을 때 검색은 묻지 않고 즉시 수행**한다 — 사용자가 답을 기다리는 상황에서 확인 질문은 방해다.

기록을 저장할 때만 승인 규칙이 적용된다.

## 언제 동작하나

별도 호출 없이 두 시점에 개입한다.

### 시점 1. 막혔을 때 — 조사보다 검색이 먼저

"뭔가 안 된다", 빌드·배포 실패, 에러 로그 붙여넣기, 원인 불명 상황이면 **조사를 시작하기 전에** 기록을 검색한다.

```bash
PROJECT_ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
PYTHON=$(for _py in python3 python; do _path=$(command -v "$_py" 2>/dev/null) || continue; "$_path" -c "import sys; sys.exit(0)" 2>/dev/null && echo "$_path" && break; done)
[ -z "$PYTHON" ] && { echo "Python not found"; exit 1; }
SKILL=pro-note; ROOT=$(git rev-parse --show-toplevel 2>/dev/null || pwd)
[ -d "$ROOT/skills/$SKILL/scripts" ] || ROOT=$(ls -d ~/.claude/plugins/cache/*/projectops/* ~/.codex/plugins/cache/*/projectops/* 2>/dev/null | sort -V | tail -1)
[ -n "$ROOT" ] || ROOT=$(ls -d ~/.gemini/extensions/projectops ~/.pi/agent/git/github.com/*/projectops 2>/dev/null | head -1)
SCRIPTS="$ROOT/skills/$SKILL/scripts"
[ -d "$SCRIPTS" ] || { echo "projectops 스킬 스크립트를 찾지 못했습니다. 플러그인 설치를 확인하세요."; exit 1; }
cd "$SCRIPTS" || exit 1
PYTHONIOENCODING=utf-8 "$PYTHON" note_cli.py search "{증상 키워드}"
```

검색어는 사용자 표현 그대로가 아니라 **증상의 핵심 명사**로 만든다. "배포가 또 안 되네요" → `배포 실패 인증서` 처럼 후보 키워드를 2~3개 조합한다.

결과 처리:

| 상황 | 행동 |
|---|---|
| 관련 기록 발견 | 그 문서를 읽고 **해결법이 지금 상황에 적용되는지 먼저 검증**한다. 맞으면 조사 없이 끝난다 |
| 결과 없음 | 처음 겪는 문제다. 아래 조사 절차로 진행한다 |

발견했을 때는 이렇게 알린다:

```
전에 겪은 문제로 보입니다.

  {기록 제목} ({언제})
  원인: {한 줄}
  조치: {한 줄}

먼저 {첫 확인 명령}부터 확인해볼까요?
```

### 시점 2. 어렵게 알아냈을 때 — 기록을 제안

해결된 모든 건을 기록하지 않는다. **고생한 흔적이 있을 때만** 제안한다.

| 제안한다 | 제안하지 않는다 |
|---|---|
| 시도를 여러 번 반복했다 | 한 번에 끝났다 |
| 원인이 처음 예상과 달랐다 | 예상대로였다 |
| 조사가 여러 단계로 길어졌다 | 즉시 답이 보였다 |
| 검색해도 과거 기록이 없었다 | 기존 기록으로 해결했다 |
| 다시 만나면 또 헤맬 것 같다 | 사소하고 일회성이다 |

한 번에 끝난 일은 남길 가치가 없고, 매번 물으면 방해가 된다.

### 명시적 호출

`/pro-note`를 직접 부르면 검색 → 정리 → 기록 전체를 수행한다. 이미 해결한 것을 나중에 기록할 때도 쓴다. 이 경우 **대화 맥락에서 조사 결과를 먼저 추출**하고 부족한 것만 보충한다 — 이미 한 조사를 반복하지 않는다.

## 기록의 두 종류

| 종류 | 담는 것 | 파일명 | 갱신 |
|---|---|---|---|
| `case` | 무슨 일이 있었나 — 증상·조사·원인·조치·검증 | `YYYYMMDD_NNN_제목.md` | 사건마다 새로 |
| `fact` | 무엇을 알게 됐나 — 재사용 가능한 사실 | `주제.md` | 주제별로 누적 갱신 |

판단 기준: **한 번의 사건이면 case, 앞으로 계속 참이면 fact.**

```
"7월 27일 배포가 인증서 만료로 실패했다"        → case
"이 프로젝트 배포 인증서는 1년마다 갱신해야 한다" → fact
```

## 저장 위치 판정

이 프로젝트에서만 의미 있는 것과, 어디서나 쓸모 있는 것을 나눈다.

```bash
PYTHONIOENCODING=utf-8 "$PYTHON" note_cli.py resolve-scope
```

판정 기준은 **저장소 파일이 바뀌었는가**다.

| 신호 | 판정 | 예시 |
|---|---|---|
| 저장소 파일 변경됨 | `project` | 이 프로젝트 코드·설정 수정 |
| 변경 없이 외부만 조치 | `home` | 인증서 갱신, 계정 설정, 로컬 런타임 설치 |
| git 저장소 밖 | `home` | — |

출력의 `ask_user`가 `true`면 확실하지 않다는 뜻이다. 이때만 근거를 제시하고 한 번 묻는다:

```
이번 건은 {원인}이 원인이었습니다.
{판정 근거}

다른 프로젝트에서도 겪을 수 있어 보이는데, 어디에 남길까요?
1. 공용 (다른 프로젝트에서도 검색됨)
2. 이 저장소에만
```

`ask_user`가 `false`면 **묻지 않고 진행**한다.

> 검색은 항상 양쪽을 모두 조회한다. 지금 막힌 것이 프로젝트 문제일지 환경 문제일지 미리 알 수 없기 때문이다.

## 조사 절차

과거 기록이 없을 때 수행한다. 유형별 확인 항목은 `references/investigation-checklists.md` 참조.

조사하면서 **실행한 명령과 그 출력을 그대로 보존**한다. 이것이 기록의 핵심 재료다. 나중에 재구성하려 하면 명령어가 부정확해지고, 그러면 기록이 쓸모없어진다.

```
1. 증상 확정      — 무엇이 안 되는가, 언제부터인가, 최근 무엇이 바뀌었나
2. 범위 좁히기    — 어디까지 정상이고 어디부터 실패하는가
3. 가설 → 검증    — 근거 있는 가설을 세우고 명령으로 확인한다
4. 원인 확정      — 증거로 뒷받침되는가. 아니면 (추정) 표기
5. 조치           — 되돌릴 수 없으면 백업 먼저
6. 검증           — 실제로 해결됐는지 확인하는 명령까지
```

## 기록 품질 자체검토

저장 직전 스스로 확인한다. 하나라도 아니면 보완한다.

- [ ] 이 문서만 보고 AI 없이 같은 문제를 해결할 수 있는가
- [ ] 모든 명령어를 복사해서 그대로 실행할 수 있는가 (경로가 구체적인가)
- [ ] 각 명령이 무엇을 확인하는지, 출력이 무슨 뜻인지 적혀 있는가
- [ ] 되돌릴 수 없는 조치 앞에 백업이 있는가
- [ ] 해결됐는지 확인하는 검증 단계가 있는가
- [ ] 왜 이 문제가 생겼는지 설명돼 있는가
- [ ] 추측을 사실처럼 쓰지 않았는가

민감 정보는 `references/common-rules.md`의 마스킹 규칙을 따른다. 실제 토큰·비밀번호·내부 IP는 플레이스홀더로 바꾼다.

## 방법론 개선 제안

같은 원인이 **3회 이상 반복**되면 이 문서(`SKILL.md`)의 조사 절차 자체를 개선할 수 있다.

```
"담당자가 설정 한 줄을 지웠다"        → case에만
"이 서비스는 컨테이너로 구동된다"      → fact에
"기동 실패 3건이 모두 설정 누락이었다"  → 방법론 개선 제안
```

**한 번 겪은 것을 방법론에 넣지 않는다.** 특수 사례가 절차를 오염시킨다.

제안할 때는 변경 내용을 보여주고 승인을 받는다. 승인 없이 `SKILL.md`를 수정하지 않는다 — 이 파일은 사용자에게 배포되는 자산이므로, 한 사람의 경험이 다른 프로젝트의 방법론을 자동으로 바꾸면 안 된다.

```
같은 원인이 3번 반복됐습니다.

  {사례 1} ({날짜})
  {사례 2} ({날짜})
  {사례 3} ({날짜})

조사 절차에 이 항목을 추가할까요?

  + {추가할 절차}
```
