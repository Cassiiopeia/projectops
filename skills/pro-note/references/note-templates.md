# 기록 템플릿 · 품질 검토 · 방법론 개선

> 언제 읽나: 기록(case/fact)을 실제로 작성·저장할 때, 또는 같은 원인이 3회 이상 반복돼 조사 절차 개선을 제안할 때.

## 기록의 독자와 품질 기준

기록의 독자는 **6개월 뒤의 누군가**다. 그 사람은 이 대화를 못 봤고, AI 도움 없이 터미널 앞에 앉아 있을 수도 있다.
그 사람이 이 문서만 보고 **같은 문제를 처음부터 끝까지 해결할 수 있어야 한다.** 이것이 유일한 품질 기준이다.

- 명령어는 **복사해서 그대로 실행 가능**해야 한다 — 경로를 구체적으로, 축약하지 않고
- 각 명령이 **무엇을 확인하기 위한 것인지**와 **어떤 출력이 나오면 무슨 뜻인지**를 함께 적는다
- 되돌릴 수 없는 조치 앞에는 **백업 절차**를 먼저 둔다
- "이렇게 하면 된다"가 아니라 **왜 이 문제가 생겼고 왜 이 조치가 맞는지**를 적는다
- 증거 없이 원인을 단정하지 않는다. 불확실하면 `(추정)`이라고 표시한다

## 막혔을 때 — 기록을 찾았을 때 알리는 형식

```
전에 겪은 문제로 보입니다.

  {기록 제목} ({언제})
  원인: {한 줄}
  조치: {한 줄}

먼저 {첫 확인 명령}부터 확인해볼까요?
```

## 저장 위치가 애매할 때(`ask_user: true`) 묻는 형식

```
이번 건은 {원인}이 원인이었습니다.
{판정 근거}

다른 프로젝트에서도 겪을 수 있어 보이는데, 어디에 남길까요?
1. 공용 (다른 프로젝트에서도 검색됨)
2. 이 저장소에만
```

## fact 템플릿

````markdown
# {주제}

## {소제목}

{알게 된 사실}

확인 방법:

```bash
{명령}
```

관련 기록: [{case 제목}]({상대경로})
````

기존 `fact` 파일이 있으면 **덮어쓰지 않고 해당 절만 갱신**한다.

## 기록 품질 자체검토

저장 직전 스스로 확인한다. 하나라도 아니면 보완한다.

- [ ] 이 문서만 보고 AI 없이 같은 문제를 해결할 수 있는가
- [ ] 모든 명령어를 복사해서 그대로 실행할 수 있는가 (경로가 구체적인가)
- [ ] 각 명령이 무엇을 확인하는지, 출력이 무슨 뜻인지 적혀 있는가
- [ ] 되돌릴 수 없는 조치 앞에 백업이 있는가
- [ ] 해결됐는지 확인하는 검증 단계가 있는가
- [ ] 왜 이 문제가 생겼는지 설명돼 있는가
- [ ] 추측을 사실처럼 쓰지 않았는가

민감 정보는 `../../references/common-rules.md`의 마스킹 규칙을 따른다. 실제 토큰·비밀번호·내부 IP는 플레이스홀더로 바꾼다.

## 방법론 개선 제안

같은 원인이 **3회 이상 반복**되면 `SKILL.md`의 조사 절차 자체를 개선할 수 있다.

```
"담당자가 설정 한 줄을 지웠다"        → case에만
"이 서비스는 컨테이너로 구동된다"      → fact에
"기동 실패 3건이 모두 설정 누락이었다"  → 방법론 개선 제안
```

**한 번 겪은 것을 방법론에 넣지 않는다.** 특수 사례가 절차를 오염시킨다.

제안할 때는 변경 내용을 보여주고 승인을 받는다. 승인 없이 `SKILL.md`를 수정하지 않는다 — 이 파일은 사용자에게 배포되는 자산이므로, 한 사람의 경험이 다른 프로젝트의 방법론을 자동으로 바꾸면 안 된다.

```
같은 원인이 3번 반복됐습니다.

  {사례 1} ({날짜})
  {사례 2} ({날짜})
  {사례 3} ({날짜})

조사 절차에 이 항목을 추가할까요?

  + {추가할 절차}
```
