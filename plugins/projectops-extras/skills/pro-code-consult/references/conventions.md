# 코딩 규칙과 클린 코드 원칙 (Flutter · Spring · Python · JavaScript 공통)

이 문서는 어떤 스택에서 코드를 쓰든 같은 기준으로 판단하기 위한 규칙이다.
목표는 하나다. **한 곳을 고치면 전체가 맞게 바뀌고, 이름만 읽어도 뜻이 보이는 코드.**
Apple풍 재디자인을 화면 수십 개에 한 번에 반영할 수 있었던 것은, 색·간격·컴포넌트를 공통 지점 한 곳에 모아 둔 덕분이다.
이 성공 방식을 모든 영역(디자인, API, 설정, 자산, 문구)에 똑같이 적용한다.

---

## 1. 핵심 원칙 세 가지

1. **단일 원본 (Single Source of Truth)**
   같은 값·규칙·자산의 원본은 한 곳에만 둔다. 다른 곳은 그 원본을 참조하거나 원본에서 생성한다. 손으로 복사한 사본은 언젠가 반드시 어긋난다.
2. **세 번째에 공통화 (Rule of Three)**
   - 같은 코드나 값이 **2곳**까지면 각자 둔다. 섣부른 추상화는 오히려 읽기 어렵다.
   - **3곳째**가 생기면 그 즉시 공통 지점으로 뽑아낸다. 미루지 않는다.
   - 예외: 브랜드 자산(로고·색·폰트), 설정값(URL·키 이름·번들 ID), 법적 문구는 **2곳이어도** 처음부터 단일 원본으로 관리한다. 이것들은 어긋나면 바로 사용자 눈에 띄거나 장애로 이어진다.
3. **이름이 곧 설명**
   이름만 보고 무엇인지, 무엇을 하는지 바로 알 수 있어야 한다. 길어져도 괜찮다. 주석으로 이름을 보충해야 한다면 이름을 다시 짓는다.

## 2. 네이밍

### 2.1 공통 규칙
| 대상 | 규칙 | 좋은 예 | 나쁜 예 |
|---|---|---|---|
| boolean 변수·프로퍼티·getter | `is` / `has` / `can` / `should` 로 시작 | `isDarkMode`, `hasUnreadNotification`, `canSubmitAnswer`, `shouldShowOnboarding` | `dark`, `flag`, `loaded`, `check` |
| 함수·메서드 | 동사로 시작해 하는 일을 말한다 | `fetchDailyQuestionSet`, `calculatePassReadinessPercent`, `saveSelectedThemeMode` | `data()`, `process()`, `handle()`, `doIt()` |
| boolean 반환 함수 | 질문형 | `isAnswerCorrect(...)`, `hasExpiredToken()` | `checkAnswer(...)` (무엇을 돌려주는지 모름) |
| 컬렉션 | 복수형 또는 `...List` / `...ById` | `questionSummaries`, `topicNameById` | `qList`, `data`, `arr` |
| 단위가 있는 숫자 | 단위를 접미사로 | `timeoutSeconds`, `bottomInsetPixels`, `retryDelayMilliseconds` | `timeout`, `delay` |
| 이벤트 핸들러 | `on` + 사건 | `onThemeModeSelected`, `onSubmitButtonPressed` | `click`, `cb` |
| 변환 함수 | `to...` / `from...` | `toQuestionDetailResponse`, `fromJson` | `conv`, `map2` |

### 2.2 금지
- **약어 금지.** `svc`, `repo`, `mgr`, `btn`, `idx`, `tmp`, `res`, `cnt`, `q`, `ctx`(프레임워크 관례 제외) 대신 풀어서 쓴다.
  - 허용하는 약어는 업계 표준뿐이다: `id`, `url`, `api`, `json`, `http`, `sql`, `ui`, `dto`, `jwt`, `uuid`.
- 의미 없는 이름 금지: `data`, `info`, `item`, `value`, `temp`, `result`, `manager`, `helper`, `util`. 단독으로 쓰지 말고 무엇의 무엇인지 붙인다(`questionDetailData` → `questionDetail`).
- 부정형 boolean 금지: `isNotVisible` 대신 `isVisible`을 쓰고 호출부에서 부정한다.
- 접두사만으로 소속을 나타내는 이름(`AppButton`)은 디자인 시스템 컴포넌트에만 쓴다. 그 외에는 역할이 드러나는 이름을 쓴다.

### 2.3 파일과 타입
- 파일 하나에 주된 타입 하나를 둔다. **파일명은 주된 타입 이름과 같게** 짓는다(`question_detail_page.dart` ↔ `QuestionDetailPage`, `QuestionService.java`, `question_service.py` ↔ `QuestionService`).
- 역할 접미사를 일관되게 쓴다.

| 역할 | Flutter | Spring | Python |
|---|---|---|---|
| 화면 | `...Page` | — | — |
| 재사용 UI | `...Widget` / 디자인 시스템 `App...` | — | — |
| 상태 | `...Provider` / `...Notifier` | — | — |
| 요청 진입점 | — | `...Controller` | `..._router` |
| 업무 규칙 | `...Service` / `...UseCase` | `...Service` | `..._service` |
| 저장소 접근 | `...Repository` | `...Repository` | `..._repository` |
| 외부 시스템 호출 | `...Client` / `...Api` | `...Client` | `..._client` |
| 요청/응답 형태 | `...Request` / `...Response` | `...Request` / `...Response` | `...Request` / `...Response` |

### 2.4 언어별 표기
- Flutter/Dart: 타입 `UpperCamelCase`, 멤버 `lowerCamelCase`, 파일 `snake_case.dart`, 상수도 `lowerCamelCase`.
- Spring/Java: 타입 `UpperCamelCase`, 멤버 `lowerCamelCase`, 상수 `UPPER_SNAKE_CASE`, 패키지 소문자.
- Python: 타입 `UpperCamelCase`, 함수·변수 `snake_case`, 상수 `UPPER_SNAKE_CASE`, boolean도 `is_...` / `has_...`로 시작.

## 3. 아키텍처: 계층과 의존 방향

### 3.1 네 계층 (모든 스택 공통 개념)
```
표현(Presentation)  →  응용(Application)  →  도메인(Domain)  ←  인프라(Infrastructure)
화면·컨트롤러·라우터     유스케이스·서비스      규칙·모델          DB·HTTP·파일·외부 API
```
- 의존은 **바깥에서 안쪽으로만** 향한다. 도메인은 아무것도 모른다.
- 표현 계층은 인프라(DB, HTTP 클라이언트)를 직접 부르지 않는다. 반드시 응용 계층을 거친다.
- 계층을 건너는 데이터는 그 계층의 형태로 바꾼다. API 응답 JSON이 화면 위젯까지 그대로 내려가지 않는다.

| 개념 | Flutter | Spring | Python (FastAPI) |
|---|---|---|---|
| 표현 | `presentation/pages`, `presentation/widgets` | `controller` | `routers` |
| 상태 | `presentation/providers` (Riverpod) | — | — |
| 응용 | `domain/usecases` 또는 `application` | `service` | `services` |
| 도메인 | `domain/models` | `domain` / `entity` | `domain` / `models` |
| 인프라 | `data/repositories`, `data/sources`, `core/network` | `repository`, `client`, `config` | `repositories`, `clients`, `config` |
| 공통 | `core/` (설정·에러·포맷), `presentation/design/` (디자인 시스템) | `common/` (응답·예외·검증) | `core/` (설정·예외·로깅) |

### 3.2 횡단 관심사는 한 곳에서
아래는 화면이나 기능마다 따로 구현하지 않는다. 처음부터 공통 지점 한 곳에 둔다.
- **에러 처리**: Spring은 `@RestControllerAdvice`, FastAPI는 exception handler, Flutter는 네트워크 계층 인터셉터와 공통 에러 변환기 하나.
- **응답 형식**: 성공·실패 응답 모양은 하나로 정한다.
- **인증 토큰**: 붙이기와 갱신은 HTTP 클라이언트 한 곳에서 한다.
- **로딩 / 에러 / 빈 상태 UI**: 공통 위젯 하나를 화면마다 재사용한다.
- **날짜·숫자·시간 포맷**: 포맷터 하나로 처리한다.
- **로깅**: 로거 설정 하나로 처리한다.

### 3.3 크기와 책임
- 한 파일·클래스는 한 가지 책임만 가진다. **300줄**을 넘으면 분리를 검토하고, 500줄을 넘으면 반드시 분리한다.
- 함수는 한 가지 일만 한다. 이름에 "그리고"가 들어가야 설명된다면 둘로 나눈다.
- 화면 파일 안에 업무 규칙(점수 계산, 정렬 기준, 검증)을 두지 않는다. 응용 계층으로 옮긴다.

## 4. 디자인 시스템 (UI가 있는 스택)

Apple풍 재디자인을 한 번에 바꿀 수 있었던 구조다. 모든 UI 코드가 이 구조를 따른다.

1. **토큰**: 색·간격·글자 크기·모서리 반경·그림자·애니메이션 시간을 한 곳(`design/tokens`)에 정의한다.
   - 라이트·다크 값은 토큰 안에서 함께 정의한다.
2. **테마**: 토큰을 묶어 라이트/다크 테마를 만든다. 다크 판정은 공통 getter 하나(예: `context.isDark`)로만 한다.
3. **컴포넌트**: 버튼·카드·목록 행·시트·로고처럼 3번 이상 쓰이는 UI는 디자인 시스템 컴포넌트로 만든다.
4. **화면**은 토큰과 컴포넌트만 조합한다.

**금지**
- 화면 코드에 색 값(`Color(0xFF...)`, `#FFFFFF`, `Colors.white`), 숫자 간격(`EdgeInsets.all(13)`), 글자 크기를 직접 쓰지 않는다. 필요한 토큰이 없으면 토큰을 먼저 추가한다.
- 자산(로고·아이콘)을 화면에서 경로로 직접 불러오지 않는다(`Image.asset('assets/logo.png')`). 컴포넌트(`AppLogo`)를 거친다.

---

### 4.1 규칙은 테스트로 강제한다
문서로만 정한 규칙은 한 번은 반드시 무너진다. 공통 지점을 만들면, 그것을 우회하는 코드를 **아키텍처 규칙 테스트**로 막는다.
- 예: 화면(feature) 코드에서 `showModalBottomSheet(`, `ListTile(`, `Color(0x`, `Image.asset(` 직접 사용을 금지한다. 공통 컴포넌트(`showAppBottomSheet`, `GroupedListRow`, 토큰, `AppLogo`)만 허용한다.
- 예외는 테스트 안에 **명시된 목록**으로만 둔다. 예외에는 이유 주석을 붙인다.
- Spring은 ArchUnit, Python은 import 검사 테스트(또는 import-linter), Flutter는 소스 스캔 테스트로 계층 의존 방향도 같은 방식으로 강제한다.
- 새 화면이나 새 기능은 이 테스트 덕분에 자동으로 같은 구조를 따른다.

### 4.2 공통화 설계안의 형식
공통화나 리팩터링을 제안할 때는 아래 순서로 보여 주고 승인을 받는다.
1. **반복 패턴 조사**: 무엇이 몇 곳에서, 어떻게 다르게 반복되는지 근거와 함께
2. **계층**: 공통 코드를 둘 폴더 구조
3. **새 공통 컴포넌트**: 각각 무엇을 한 번에 처리하는지
4. **이름 표**: 지금 이름, 바꿀 이름, 이름만 보고 알 수 있는 것
5. **적용 범위**: 동작은 그대로 두고 구조만 바꾸며, 기존 테스트를 안전망으로 쓴다
6. **규칙 테스트**: 무엇을 금지하고 무엇을 예외로 둘지
7. **문서**: 아키텍처 문서와 결정 기록
8. **하지 않는 것**: 과한 도구나 범위를 명시

## 5. 브랜드 자산·설정·문구: 플랫폼을 넘는 단일 원본

같은 로고가 Flutter 에셋, iOS 시작 화면, Android 리소스, 웹, 관리자 페이지, 스토어 이미지에 각각 있으면, 하나를 고칠 때 나머지를 반드시 놓친다.

- **원본 폴더를 하나 둔다**(예: 레포 루트 `brand/`). 로고 원본(투명 배경, 라이트·다크), 아이콘 원본, 색 정의를 여기에만 둔다.
- 각 플랫폼 사본은 **원본에서 생성하는 스크립트**로 만든다. 사본을 손으로 고치지 않는다.
  - 예: `brand/generate_platform_assets.py` → Flutter `assets/`, iOS `LaunchImage`·`AppIcon`, Android `mipmap`, 웹 `favicon`.
- 설정값(API 주소, 번들 ID, 앱 이름, 버전)도 원본을 하나 둔다. 각 플랫폼은 그 값을 읽어 쓴다.
- 법적 문구(이용약관·개인정보처리방침)와 API 계약(요청/응답 형태, 에러 코드)도 원본을 하나 둔다. 계약은 서버의 OpenAPI 스펙에서 클라이언트 타입을 생성한다.

## 6. 상수와 매직 값
- 의미 있는 숫자·문자열은 이름 있는 상수로 둔다(`maximumDailyQuestionCount = 3`).
- 상수는 쓰이는 범위에 맞는 곳에 둔다.
  - 한 클래스 안에서만 쓰면 그 클래스 안에 둔다.
  - 여러 곳에서 쓰면 공통 상수 파일에 둔다.
  - 플랫폼을 넘으면 5장의 단일 원본에 둔다.
- 저장소 키·이벤트 이름·라우트 경로 같은 문자열 식별자는 상수 한 곳에서 관리한다(`AppRoutes`, `StorageKeys`).

## 7. 주석

주석은 **줄글이 아니라 필요한 정보만** 적는다. 한국어로 쓰고, 명사형이나 짧은 구로 끝낸다("~합니다", "~하기 위해서는" 같은 문장 금지).
코드를 위에서 아래로 훑었을 때 **주석만 읽어도 처리 흐름이 보여야** 한다.

### 7.1 메서드·클래스 문서 주석: 한 줄 요약
- 무엇을 하는지 한 줄로 쓴다. 단계가 있으면 `>`로 흐름을 적는다.
- 변환이나 매핑은 `입력 > 출력` 형태로 쓴다.
```java
/**
 * 문제 1건 채점: 검증 > 샌드박스 실행 > 결과 비교 > 점수 저장
 */
/**
 * 난이도 코드(1, 2, 3) > 표시 이름(쉬움, 보통, 어려움)
 */
/**
 * 로그용 값 정리 (제어문자·비ASCII > ?, 100자 제한)
 */
```

- 클래스 문서 주석은 두 줄 이내로 쓴다. 첫 줄은 `대상: 책임1, 책임2, 책임3`, 둘째 줄은 동작 구조 한 줄이다.
```java
/**
 * 외부 연동 API 공통: 사용 조건 확인, 토큰 발급, 토큰 검증
 * 사용 조건 3개(사이트, 사용 옵션, 허용 IP) > 요청마다 설정 조회
 */
```
- 조건이나 대상이 여러 개면 개수와 목록을 함께 쓴다: `조건 3개: A, B, C`
- 하지 않는 일도 범위로 한 줄 적는다: `그 외 상태는 기록하지 않음`

### 7.2 로직 안 단계 주석: 블록마다 머리글
- 의미 있는 블록 앞에 한 줄 머리글을 단다. 이것만 이어 읽으면 알고리즘이 된다.
- 괄호로 **무엇을 다루는지 나열**한다.
```java
// 요청 검증 (필수값, 허용 문자, 크기, 중복)
// 건별 처리
// 저장된 건 있으면 캐시 갱신 1회
// 실패 시 백업 복원
```

### 7.3 값과 코드의 뜻을 바로 옆에
- 코드값, 상태값, 플래그의 의미를 그 자리에 적는다.
```java
// mode 필수: 1 연습, 2 실전, 3 전체
// is_applied: 정책에서 사용 중 1, 아니면 0
```
- 상수에는 용도와 단위를 적는다: `// 업로드 파일 최대 크기 (10MB)`
- 단위는 가능하면 이름에 넣는다: `TOKEN_VALID_SECONDS`, `MAX_UPLOAD_BYTES`
- 설정 키 상수에는 **어디의 어떤 값인지와 값의 뜻**을 적는다.
```java
// app_settings: 외부 API 사용 여부 (1:사용 0:미사용)
private static final String SETTING_KEY_EXTERNAL_API_ENABLED = "externalApiEnabled";
// app_settings: 호출 허용 IP 목록 (쉼표 구분)
private static final String SETTING_KEY_EXTERNAL_API_ALLOWED_IPS = "externalApiAllowedIps";
private static final String ALLOWED_IP_DELIMITER = ",";
```
- 관련 상수는 묶어서 나란히 둔다(키 다음에 그 값의 구분자 등).
- 경로나 형식은 실제 모양을 예시로 적는다: `// 백업: {home}/backup/{파일명}_{yyyyMMddHHmmss}`

### 7.4 순서와 예외 조건
- 순서나 "항상 실행" 같은 조건은 짧은 괄호로 남긴다: `(개인키 먼저)`, `(성공·실패 공통)`, `(예외 시에도 기록)`.
- 비교는 `A <-> B`로 쓴다: `// 인증서 공개키 <-> 개인키에서 계산한 공개키`

### 7.5 왜(WHY)와 연결된 위치
- 코드만 봐서는 이유를 알 수 없을 때만 이유를 쓴다. 이때도 한 줄로 쓴다.
- 다른 곳과 묶여 있어 함께 바꿔야 하는 값에는 그 위치를 적는다: `// build.gradle.kts 가 android/app 기준으로 읽음`
- 근거 이슈 번호를 남긴다: `(#453)`

### 7.6 AI가 흔히 만드는 주석 문제 (금지)
- **건드리지 않은 코드의 기존 주석을 고치거나 다시 쓰지 않는다.** 바꾼 코드에 딸린 주석만 손댄다.
- **로직을 바꾸면 그 위 주석과 감싼 함수의 문서 주석을 같이 확인한다.** 옛 동작을 설명하는 주석은 없는 것보다 나쁘다.
- 한 줄이면 될 것을 여러 줄 설명문으로 쓰지 않는다. 주석이 코드보다 길면 잘못된 것이다.
- 매 줄마다 주석을 달지 않는다. 블록 머리글(7.2)만 단다.
- 작업 경위를 주석에 남기지 않는다: `// 기존에는 X였는데 Y로 바꿈`, `// 이전 버그 수정`, `// 리팩터링으로 추가`. 경위는 커밋·이슈에 남긴다.
- 당연한 것을 강조하지 않는다: `// 중요!`, `// 주의: 이 함수는 사용자를 저장합니다`.
- 주석 끝에 "~합니다/~입니다/~하기 위함" 같은 문장체를 쓰지 않는다.

### 7.7 쓰지 않는 주석
- 이름을 그대로 반복하는 주석: `// 사용자를 저장한다` 위에 `saveUser()`
- 여러 줄짜리 설명문, 변경 이력, 작성자, 주석 처리한 옛 코드

### 7.8 로그 문구
- 로그는 영어로 쓰고, 기능 접두사를 고정한다: `[question grade] rejected 400 : answer is empty`
- 거부와 실패에는 상태 코드와 원인을 적고, 외부에서 들어온 값은 정리(sanitize)한 뒤 넣는다.
- 핵심 변화는 전후 값을 남긴다: `replaced : serial A -> B`

## 8. 리팩터링을 보는 시각

파일 하나를 열었을 때 아래가 보이면 리팩터링 대상이다. 위에서부터 우선한다.

| 신호 | 이렇게 바꾼다 |
|---|---|
| 한 메서드에 단계가 여러 개 섞여 있다 | 단계마다 이름 있는 private 메서드로 나눈다. 공개 메서드는 단계 호출만으로 흐름을 보여 준다(7.1의 `검증 > 처리 > 결과`) |
| 검증이 본 로직 사이사이에 흩어져 있다 | 맨 앞 검증 메서드로 모은다. 실패하면 바로 반환한다(guard clause). 건별 검증은 실패 이유 문자열을 돌려줘서 로그에 남긴다 |
| 검사 결과가 boolean이라, 호출부가 왜 거부됐는지 다시 따진다 | 검사 메서드가 **거부 사유가 담긴 결과**를 돌려주게 한다(상태 코드·사유 enum·사유 문자열). 성공은 하나, 실패는 사유별로 구분한다 |
| 사용 조건·권한 확인이 여러 진입점에 복사돼 있다 | 조건 확인 메서드 하나로 모으고, 모든 진입점(발급·검증 등)이 그것을 거친다 |
| 조건식이 길어 뜻을 읽어야 안다 | 질문형 이름의 메서드로 뺀다: `isValidFileName()`, `isPublicKeyPairMatched()`, `hasReplacedCertificate()` |
| 코드값 변환·매핑이 여러 곳에 있다 | 변환 메서드 하나로 모은다: `toDifficultyLabel(code)` |
| 실패해도 꼭 해야 할 일(감사 로그, 임시 파일 삭제)이 성공 경로에만 있다 | `finally`로 옮기고 주석에 `(성공·실패 공통)`을 적는다 |
| 일부만 바뀐 채로 실패할 수 있다 | 변경 전 백업 > 변경 > 확인 > 실패 시 복원 순서를 명시적으로 짠다 |
| 외부 입력이 로그·파일 경로·명령에 그대로 들어간다 | 정리(sanitize)·경로 이동 차단·이스케이프 메서드를 거치게 한다 |
| 의미 있는 숫자·문자열 리터럴이 있다 | 이름 있는 상수로 두고 용도와 단위 주석을 단다 |
| 같은 코드가 3곳에 있다 | 공통 지점으로 뺀다(1장 세 번째 원칙) |
| 300줄이 넘는다 | 책임별로 클래스를 나눈다(3.3) |

동작은 바꾸지 않고 구조만 바꾼다. 기존 테스트를 안전망으로 쓰고, 없으면 리팩터링 전에 현재 동작을 고정하는 테스트를 먼저 만든다.

## 9. 수정할 때의 절차 (Claude Code 작업 규칙)

1. **전수 조사 먼저.** 고칠 대상의 모든 사본과 사용처를 찾는다.
   - 새 함수·위젯·클래스를 만들기 전에 비슷한 이름이 이미 있는지 검색한다. 있으면 재사용하거나 그것을 고친다.
   - 같은 계층의 모범 파일(`docs/architecture/stacks/<스택>.md`에 지정)을 먼저 읽고 그 모양을 따른다.
   - 같은 이름, 같은 값, 같은 파일 해시로 검색한다.
   - Flutter 화면만 보지 말고 iOS·Android 네이티브, 웹, 서버 정적 자원, 스토어 이미지, 문서까지 포함한다.
2. **원본에서 고친다.** 공통 지점이 있으면 거기를 고친다. 없고 사용처가 3곳 이상이면 공통 지점을 먼저 만든다.
3. **이름을 점검한다.** 새로 만들거나 건드린 이름이 2장 규칙(특히 boolean `is` 접두사, 약어 금지)을 지키는지 본다.
4. **실제로 띄워서 확인한다.** 라이트·다크, iOS·Android, 모든 영향 화면을 직접 실행하고 캡처한다. 테스트 통과만으로 완료라고 하지 않는다.
5. **남는 사본을 보고한다.** 이번에 못 고친 사본이 있으면 완료 보고에 위치를 적는다.

### 완료 전 점검표
- [ ] 바꾼 로직 위의 주석이 지금 동작을 설명한다 (낡은 주석 없음)
- [ ] 새로 만든 것과 비슷한 기존 코드가 없다 (있으면 재사용)
- [ ] 동결 목록(`docs/architecture/rules/*.allow`)에 줄을 더하지 않았다
- [ ] 같은 대상의 모든 사본·플랫폼을 찾았다
- [ ] 화면 코드에 하드코딩한 색·간격·자산 경로가 없다
- [ ] 3번 이상 반복되는 코드가 남아 있지 않다
- [ ] boolean 이름이 `is/has/can/should`로 시작한다
- [ ] 약어나 의미 없는 이름이 없다
- [ ] 300줄을 넘는 파일을 새로 만들지 않았다
- [ ] 주석이 줄글이 아니라 한 줄 요약·단계 머리글·값의 뜻으로 되어 있다
- [ ] 공개 메서드만 읽어도 처리 흐름이 보인다(단계별 private 메서드)
- [ ] 라이트·다크와 각 플랫폼에서 실제로 확인했다
